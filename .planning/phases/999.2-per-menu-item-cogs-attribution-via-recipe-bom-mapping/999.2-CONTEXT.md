# Phase 999.2: Per-menu-item COGS attribution via recipe/BOM mapping - Context

**Gathered:** 2026-06-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Link Toast menu items to purchase ingredients using a `recipes` table that stores a rough `usage_pct` per (menu_item, purchase_item) pair. Compute per-dish ingredient cost on demand by allocating each week's window-sum of `purchase_line_items` spend through those percentages. Expose the result via a service-token `GET` endpoint that sales-processor calls to render the weekly "COGS by Menu Item" + "Unallocated COGS" rows.

The phase delivers:

- DB migration: `recipes` table (menu_item_id FK, purchase_item_id FK, usage_pct NUMERIC(5,2), updated_at; unique on the pair)
- Recipes tab in `inventory.html` — ingredient-first edit surface, sibling of the Menu tab from Phase 22
- Sum constraint enforced server-side: `SUM(usage_pct) per purchase_item` cannot exceed 100, with a live running total in the UI
- `GET /api/v1/inventory/menu-cogs` endpoint (Bearer auth, mirrors Phase 21 patterns)
- Weekly drift check (Monday HQ scheduler) that fires Cliq + in-app banner when allocations get stale

Out of scope (locked by ROADMAP and confirmed):
- Real-time ingredient consumption tracking — allocation math runs only at report time
- Multi-vendor / multi-size purchases of the same ingredient — assume single canonical `purchase_item` per ingredient
- Per-unit BOM with actual gram-level recipes — usage % is intentionally rough
- The sales-processor rendering side — handed off via a contract document (same pattern as Phase 21)

</domain>

<decisions>
## Implementation Decisions

### Recipes Tab UX & Placement

- **D-01:** New sibling tab placed between Menu and Trends. Tab order becomes: Purchases / Stock / Menu / **Recipes** / Trends / Cost / Setup. Resolves the open question Phase 22 D-08 left for this phase.
- **D-02:** Each ingredient row is **collapsed by default**, tap to expand. The collapsed row shows ingredient name, last week's spend, and `Unallocated: X%`. Expanded view reveals the allocated menu items with their %.
- **D-03:** `%` edits **autosave on blur** per row (matches `workflows.html` `autoSaveField` pattern documented in CLAUDE.md). No save button. On server-side 422 (sum > 100), inline error names the conflicting menu item and the edit rolls back.
- **D-04:** When the owner taps `+ Add menu item` on an ingredient row, the fullscreen picker shows **all menu items, except those already allocated to this ingredient**. Items allocated to OTHER ingredients still appear (correct — chicken can be in multiple dishes).
- **D-05:** The `%` editor is a **slider with 5% snap points**. Net-new component — no existing slider in `inventory.html`. Planner needs to spec the touch interaction.
- **D-06:** A **read-only per-menu-item summary section** sits below the ingredients list on the same Recipes tab. Tap a menu item → shows its ingredients with % and `$` contribution. Sanity-check surface only — editing is always ingredient-first.
- **D-07:** When a Toast menu item disappears (rename, removal, no sales), its recipe rows **persist**. The weekly drift check (D-21) surfaces "menu items in recipes with no sales last week" as one of the warning types.
- **D-08:** Ingredient rows support a **merge action** for stale menu items — owner picks "merge into [other menu item]" and the recipe row's FK re-points to the new master_id. Mirrors the existing vendor/item merge pattern.
- **D-09:** Toast permits **multiple menu items with the same name across different menus** (`Soda` in `Beverage/Drinks` and in `Special/Promotions`). The picker AND the read-only per-menu-item summary must show `menu_group` (and `menu_subgroup` when present) alongside the name for disambiguation.

### Cost Reference Price

- **D-10:** `ingredient_cost_per_unit` is computed from the **window-sum of `purchase_line_items.quantity * price`** within `[from..to]` for each `purchase_item`. This is the same math basis Phase 21's `cogs_excl_tax` uses, so totals reconcile across endpoints (sum of `menu-cogs` ingredient_cost_total + unallocated_cogs ≈ period-summary cogs).
- **D-11:** Cost numbers are **tax-inclusive**. Tax is pro-rated to each line item by its share of the event subtotal: `line_total_incl_tax = (qty * price) * (event.total / event.subtotal)`. Reported numbers match what the owner actually paid.
- **D-12:** **Any `purchase_items` row can be allocated** — no `is_food` flag. Owner decides what's worth mapping in the Recipes tab; anything they don't map flows to `unallocated_cogs`. Tradeoff: Recipes tab will contain non-food rows (paper towels, packaging) the owner has to scroll past or choose to allocate to specific dishes.

### menu-cogs Endpoint Contract

- **D-13:** **HQ is the truth source for `units_sold`.** The endpoint joins `recipes` → `menu_items` → `daily_menu_sales` internally. Sales-processor becomes a thin "fetch and render" consumer with no aggregation logic.
- **D-14:** `GET /api/v1/inventory/menu-cogs?from=YYYY-MM-DD&to=YYYY-MM-DD` — exact mirror of Phase 21's `period-summary`. Same Bearer auth via `HQ_INVENTORY_SERVICE_TOKEN`, same 503-if-unset behavior, idempotent and cacheable.
- **D-15:** **No completeness gate field** in the response. Always returns 200 (given valid dates + auth). Drift surfaces in-app via the Recipes-tab banner and weekly Cliq — not as an endpoint-level boolean.
- **D-16:** Default response is summary only — one row per `menu_item` with `units_sold`, `ingredient_cost_per_unit`, `ingredient_cost_total`. Pass `?breakdown=true` to receive per-ingredient detail per menu item (each menu_item entry gets an `ingredients: [{purchase_item_description, usage_pct, allocated_cost}]` array).
- **D-17:** `unallocated_cogs` shape:
  - Default: `unallocated_cogs: <number>` — single dollar residual.
  - With `?breakdown=true`: `unallocated: {total: <number>, by_ingredient: [{purchase_item_description, amount, reason}]}` where `reason` is `"no recipe"` or `"partial allocation (X%)"`.
- **D-18:** Error responses **mirror Phase 21 exactly**:
  - 400 — invalid date range (missing/malformed/from > to)
  - 401 — Bearer missing or wrong
  - 503 — `HQ_INVENTORY_SERVICE_TOKEN` env var unset
  - 500 — DB/internal failure
  Same JSON envelope shape as `period-summary`.

### Drift Check Delivery

- **D-19:** Drift warnings surface in **two channels**: (1) Zoho Cliq message in the `purchaseandinventory` channel with a deep-link to the Recipes tab, (2) persistent in-app banner on the Recipes tab. No email digest for now.
- **D-20:** **Weekly scheduled job in HQ** runs the drift check — Monday morning Chicago time, mirroring the Phase 17 cutoff scheduler pattern. Computed once per week against the prior week's data. Not driven by the `menu-cogs` endpoint.
- **D-21:** Drift-check flagging thresholds (stricter than ROADMAP defaults):
  - **Unallocated > 10%** — `purchase_item` whose `SUM(usage_pct) < 90%` AND had > $0 spend last week.
  - **Divergence > 20%** — recipe row whose configured `usage_pct` differs from last week's actual implied usage by > 20 percentage points.
  - **Zero-sales drift** — menu items appearing in any recipe row with 0 units sold last week (from D-07 persistence behavior).
- **D-22:** Banner ack UX: **no dismiss button**. The banner always displays the latest weekly drift check result; on the next Monday's run, it refreshes — items still drifted persist, fixed items drop off, clean weeks clear the banner entirely. Self-healing, no per-user dismissed_at state.

### Claude's Discretion

The following decisions are not user-locked — planner / researcher should choose sensibly within these constraints:

- Exact slider UX details (drag thumb size, hold-to-fine-tune, keyboard accessibility) — D-05 locks the snap-point model only.
- Cliq message body format (just names vs names + $ amounts + percentages) — Phase 17 alert utilities are the reference.
- Drift-check job mechanism — separate goroutine ticker vs reusing an existing scheduler in `cmd/server/main.go`. Phase 17 cutoff scheduler is the pattern.
- HTTP response Cache-Control headers for `menu-cogs` (callers can cache for the duration of the window).
- Whether drift-check failures (e.g., `daily_menu_sales` gaps from a Toast outage) suppress the run or fire an "ingest stale" warning.
- Sub-cent rounding policy and how to handle `price = 0` line items (gifts/samples) — assume both are rare.
- DB cascade behavior on the `recipes` FKs — likely `ON DELETE CASCADE` for `menu_item_id` per D-07's "persist as-is" guidance is reversed: if menu_item row is hard-deleted (rare — Toast doesn't delete, it renames), we DO want cascade to clean up orphans. Worth confirming during planning.

</decisions>

<specifics>
## Specific Ideas

- **D-09 driven by user input** — "toast allow multiple menus to have items with the same name" — needs disambiguation in picker AND read-only summary.
- **D-13 driven by user input** — "HQ should become the source of truth. sales-processor would just fetch info from HQ to place into report." This single line reshaped the endpoint contract from POST-with-units-in-body to a plain GET.
- **D-21 user override** — picked stricter thresholds (10% / 20%) instead of the ROADMAP defaults (20% / 30%). Indicates the owner wants tighter signal-to-noise once recipes settle.
- **D-12 user override** — picked the "anything allocatable, no flag" path over the per-group toggle. Owner accepts the clutter cost for the schema simplicity.

</specifics>

<deferred>
## Deferred Ideas

- **Bulk-buy distortion** — a single olive-oil purchase covering 6 weeks shows as $X spend in week 1 and $0 in weeks 2-6, producing noisy per-unit COGS for slow-turn ingredients. Accepted as a known limitation; window-sum basis preserves Phase 21 consistency. Could be addressed in a follow-up phase with a trailing-N-week smoothing option if it proves problematic.
- **Per-unit BOM (gram-level recipes)** — explicitly out of scope per ROADMAP. Future phase if rough % stops being good enough.
- **Multi-vendor / multi-size purchases of same ingredient** — explicitly out of scope. Assume one canonical `purchase_item` per ingredient.
- **Real-time consumption tracking** — out of scope. Computation runs at report time only.
- **Configurable drift thresholds** — D-21 locks 10%/20% in code. If too noisy, surface a settings page in a future phase.
- **Bulk-import seeding** — no CSV-import shortcut for the first wave of recipe entries. Owner walks the Recipes tab top-down per ROADMAP estimate (~1 evening).
- **Email digest channel** — D-19 picks Cliq + in-app banner only. Email could be added later if Cliq is missed.
- **Inverse view editing** — D-06 locks the per-menu-item section as read-only. If owner ever wants to edit per dish, that's a future phase.
- **Per-item resolve / dismiss for drift banner** — D-22 locks "no ack UI." If banner noise becomes a problem, a dismiss-for-this-week button could be added.

</deferred>
