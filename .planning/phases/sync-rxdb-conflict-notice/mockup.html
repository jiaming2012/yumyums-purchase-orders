Overwritten answers

Card sync-rxdb-conflict-notice — what a crew member sees when their offline answer loses to master-wins, and how they get it back.

RxDB's default conflict handler is unconditional master-wins, verified at W2 (proof-lww.js): the later local write is discarded, the earlier server write survives, no clock participates, and error$ emits nothing. The one signal that fires is conflict$, which carries the whole discarded document. Every plate below is drawn from what that event actually contains — see UI-SPEC.md §"What conflict$ gives you" for the verbatim evidence and the limits.

Nine plates, one per State Enumeration Table row plus the design's own limits panel. Everything is inert.

success

Trigger: replication reconnects; conflict$ emits for one document; the diff names ≥1 template-backed field with a value in input.newDocumentState. Contract: amber banner above the checklist list with an exact count; the sheet shows the crew member's value and the server's side by side, labelled Yours / Now shows; every recoverable row offers Restore mine; a restored row turns green, names the value that came back, and offers Undo.

Why “Restore mine” is safe, and not magic. Master-wins discarded the fork because the plugin's compare-and-swap found the server value had moved. Tapping Restore writes the crew member's value again now, from the current master state — an ordinary local edit that pushes cleanly. It resurrects nothing and needs no new sync plumbing. If the server moves again in between, that write conflicts in turn and lands in this same sheet (see the error plate).

error

Trigger: Restore mine is tapped and the write does not land — the phone is offline, or the server value moved again and the restore conflicted in turn. edge · no discarded value available

Trigger: conflict$ fired, but the diff between input.newDocumentState and output yields nothing showable — either the only difference is bookkeeping (with _modified declared in the schema, any server-side touch becomes a conflict — W2 sharp edge 11), or the field is absent/null in the discarded document because the local write cleared it. Contract: the row must NOT claim an answer was lost and must NOT show an empty value where a number goes; the value slot reads Not recoverable in muted italic, one line says why in plain words, and the only action is Dismiss — no Restore button, because there is nothing to put back. The banner counts it on a separate, quieter line.

The monospace field id is deliberate. The template no longer holds a label for it, and the alternatives are both worse: a made-up title would misattribute the answer, and hiding the row entirely would silently drop the exact value this card exists to recover. Copy is a real recovery on a phone — it goes into a message to the manager in two taps.

edge · local conflict log unreadable

Trigger: the sheet opens and the local store the conflict records live in cannot be read — iOS/Safari evicted it under storage pressure, or the browser is in private mode. W3 named this the largest untested unknown for a phone-first PWA, so it gets a designed state rather than a stack trace. Contract: red-bordered card, no fabricated count, and the copy says the records are gone rather than implying the answers are — a crew member must not read a storage failure as “my work was deleted”.

what this design cannot do

Not a state — the honest boundary of the mechanism, here so the sign-off is given with it in view.

Three things no UI can fix

1. If nothing was subscribed, nothing is ever known. conflict$ is a plain RxJS Subject — no replay, no buffer. Subscribe where the replication is constructed or the event is gone. RxDB persists nothing about a resolved conflict, so the app must write the discarded value to durable local storage the instant the event arrives, or a reload loses the thing this whole screen exists to recover. Every plate above assumes that record exists. Where it lives is the UI card's call, not this mockup's.

2. Only the leader tab sees it. waitForLeadership defaults to true in a browser, so one tab replicates and the others follow — and only that tab's conflict$ fires. Two HQ tabs open, the wrong one closes, and the notice never appears. The banner must therefore read from the shared local record, not from a live subscription.

3. “Dana M., 6:12 PM” is only as real as the row. conflict$ carries no author and no timestamp of its own — every attribution above comes from fields on the document. If the replicated schema doesn't carry who-and-when, those lines must degrade to “someone else” rather than be invented. That schema belongs to sync-rxdb-schema-and-replication; this mockup is stating a requirement on it, not deciding it.
