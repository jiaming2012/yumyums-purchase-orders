# Phase 22.1 Plan 04: Combined sync+ingest worker with Cliq degradation alert Summary

**Refactored `backend/internal/toast/worker.go` to a combined sync+ingest cycle that calls `SyncDate` per date in the window, then `RunIngest` once for the window — with a consecutive-Spaces-failure counter that fires a single Zoho Cliq alert on the 3rd failed tick (D-06), and a graceful boot when DO Spaces is unconfigured (Pattern 2).**

## Accomplishments

- `StartWorker(ctx, cfg Config)` signature preserved verbatim — pre-Plan-05 `cmd/server/main.go` compiles and runs unchanged
- Top-of-`StartWorker` guard: if `cfg.SpacesClient == nil || cfg.SpacesBucket == ""` → logs `WARNING: toast worker: DO Spaces not configured — ingest disabled (server continues)` and returns. Receipt worker, HTTP API, and other subsystems boot normally (Pattern 2 graceful-degradation)
- `runCycle` now follows the D-04 combined flow:
  1. `isColdStart` → 90d (cold) or 7d (steady) window selection (D-02 preserved)
  2. For each date `d` in window: `wrote, sErr := SyncDate(ctx, cfg, d)`; classifies result as miss (D-05 INFO log only), systemic error (counter eligible), or clean write
  3. After sync loop: single `RunIngest(ctx, cfg.Pool, cfg, fromDate, toDate)` call reads Spaces → DB
  4. If RunIngest returns a precondition error → adds to systemic flag (defensive — main guard should have caught it)
  5. Failure bookkeeping: counter increments on systemic-flag tick; if `consecSpacesFails >= 3 && !alertFiredAtThreshold` → fire one Cliq alert + latch
  6. Clean tick → counter + latch reset to zero (with recovery log line if either was nonzero)
- D-05 exact format: `log.Printf("toast sync: skip %s (not in SFTP)", dateDir)` on `errors.Is(sErr, ErrSFTPMiss)`
- D-06 exact message: `"Toast sync degraded: 3 consecutive failed ticks talking to DO Spaces. Last error: %v"` formatted with `lastSyncErr` and routed via `alerts.ChannelZohoCliq`
- D-13 per-cycle summary preserved in BOTH clean and degraded paths — operators get observability whether the cycle succeeded fully or partially
- `SetAlertQueue(q *alerts.Queue)` exported — Plan 05's `main.go` will call this once before `StartWorker`
- Three new package-level vars (`alertQueue`, `consecSpacesFails`, `alertFiredAtThreshold`) all documented with the single-worker concurrency assumption noted in comments
- `cd backend && go build ./...`, `cd backend && go vet ./internal/toast/...`, and `cd backend && go test ./internal/toast/... -count=1` all green

## Decisions Made

- **Used `refactor` commit type, not `feat`.** Per Plan 02 SUMMARY's commit-type conventions: signature-preserving rewrites of internal behavior are refactors. The exported `SetAlertQueue` IS new surface area, but it's no-op until Plan 05 wires it, so the net behavior change for callers as of this commit is internal-only. (Plan 05 wiring will likely use `feat` for the main.go side.)
- **Threshold check uses `>=3` (not `==3`).** The plan said "on 3rd consecutive failure," and the latch ensures we fire only once. Using `>=3` is defensive against a hypothetical race or test that bumps the counter by more than one — the latch is the real gate, and `>=3` makes the intent ("threshold crossed") more readable than `==3` ("exactly equal to threshold").
- **`fireDegradedAlert` lives outside `runCycle`.** The plan body could have inlined the 8-line dispatch — pulling it out as a named function makes the threshold-handling block in `runCycle` read as policy ("if degraded, fire alert"), not implementation ("if degraded, marshal an alerts.Alert struct and call Enqueue"). Also gives a single grep target for testing the dispatch path in future iterations.
- **`lastSyncErr` is plain `error`, not wrapped.** The plan's message format is `"Last error: %v"`. `%v` on a wrapped error walks the chain via `.Error()` and prints the leaf message verbatim, which is what we want operators to see. No `errors.New(fmt.Sprintf(...))` wrapping — the worker's `lastSyncErr` literally is whatever `SyncDate` or `RunIngest` returned.
