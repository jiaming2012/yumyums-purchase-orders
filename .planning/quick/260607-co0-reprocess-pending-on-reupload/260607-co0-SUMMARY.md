# Quick Task 260607-co0: Reprocess Pending on Re-upload Summary

JWT auth / database / framework one-liner: receipt worker now reprocesses pending rows whose Mercury tx received a receipt after the initial poll, and the FE sync chip surfaces `auto-added` + `skipped` counts conditionally.

## What Shipped

Two-task plan executed end-to-end in 3 atomic commits:

### Task 1 — Backend classify + upgrade flow

1. **Test seams** in `backend/internal/receipt/worker.go` (lines 20-33): three package-level vars `fetchTransactions`, `parseReceipt`, `downloadReceiptFileFn` initialised to their exported counterparts. Production callers in `runIngestCycle` now route through these vars; exported `FetchTransactions` / `ParseReceipt` signatures are unchanged.

2. **`classifyExistingTx`** (worker.go lines 462-498): single-roundtrip UNION-ALL query returning `(kind, reason, error)` where `kind ∈ {none, event, pending}`. Behaviour:
   - `purchase_events` row → `("event","",nil)`
   - confirmed pending row → `("event", reason, nil)` (idempotent like a locked purchase)
   - still-open pending row → `("pending", reason, nil)` (caller decides whether to upgrade)
   - discarded pending row → `("none","",nil)` (user discarded; re-ingest allowed)
   - empty DB → `("none","",nil)`

3. **3-way switch** in `runIngestCycle` (worker.go lines 158-187): replaces the binary `bankTxIDExists` short-circuit. `kind==event` → `skippedCached++` and continue. `kind==pending` → continue UNLESS `reason=='no_attachment_on_bank_tx' && len(tx.Attachments) > 0`, in which case set `isUpgrade = true` and fall through. `kind==none` → fall through.

4. **`isUpgrade` plumbing**:
   - **Parse-fail / validate-fail / save-fail** → new `routePending` dispatcher (worker.go lines 444-449) calls `updatePendingPurchase` when isUpgrade, otherwise `insertPendingPurchase`. No ON CONFLICT skipping on upgrade rows.
   - **Auto-create** → `createPurchaseEvent` gains `isUpgrade bool` parameter (worker.go line 389). When true, the first statement inside the existing `pool.Begin` dbTx is `DELETE FROM pending_purchases WHERE bank_tx_id=$1` (worker.go lines 401-410), so the pending row removal and the event insert commit atomically.

5. **`updatePendingPurchase`** (worker.go lines 522-573): mirror of `insertPendingPurchase` field-for-field but issues `UPDATE … WHERE bank_tx_id=$1`. Preserves the row's UUID PK so any FE references remain stable. `rowcount==0` is treated as success (concurrent confirm/discard race — fine, next poll re-classifies).

6. **`bankTxIDExists` deleted.** The old 2-way idempotency helper is gone.

### Task 2 — Frontend sync chip

7. **`inventory.html` `renderSyncUI`** (lines 367-380): chip text now built from a `parts` array — `'N processed'` is always present; `'M auto-added'`, `'K pending review'`, `'C skipped'` only when their count is > 0. Joined with `', '`. Format preserved so the existing Playwright assertion against `'5 processed'` / `'2 pending review'` substrings still matches.

8. **`sw.js`** regenerated via `node build-sw.js` so the inventory.html content hash refreshes for Workbox cache invalidation. Output: `SW built: 21 files precached (1363.3 KB)`.

## Deviations from Plan

- **Added `routePending` dispatcher helper** that wasn't in the plan text. The plan said to inline `if isUpgrade { updatePendingPurchase(…) } else { insertPendingPurchase(…) }` at three call sites. A one-line helper at the same level reads cleaner and centralises the cold-vs-upgrade routing decision. Same observable behaviour.
- **Test stub `tx.Amount` sign correction.** First impl run revealed the upgrade-success test failed at `ValidateReceiptData`: Mercury debits are negative (`-bankAmount`), but my initial test stub used `Amount: 42.50` positive. Updated to `Amount: -42.50` plus `TotalUnits: 1` so the items-count vs units+cases check also passes. This was a test-bug fix, not a deviation in production code.
- **No `confirmed_by` foreign-key seed in `TestClassifyExistingTx/confirmed`**: the plan suggested seeding confirmed_at + confirmed_by. The `confirmed_by` column references `users(id) ON DELETE SET NULL` and the test fixture doesn't have a user. Set `confirmed_at = now(), confirmed_by = NULL` — the WHERE clause only filters on `confirmed_at IS NOT NULL` so the classify still returns `event` correctly. No behavioural change.
