# Summary

Added a `tracked_bank_tx_ids` array to the `/api/v1/inventory/period-summary`
JSON response. It contains every Mercury `bank_tx_id` HQ has touched for
the period, across all states (confirmed in `purchase_events`;
pending / confirmed / discarded in `pending_purchases`).

Sales-processor (next phase) will fetch Mercury directly for the pay
period and diff against this list to detect transactions Mercury knows
about but the receipt worker hasn't ingested yet — a hole the existing
`completeness.ready` gate cannot catch.

## SQL

```sql
SELECT DISTINCT bank_tx_id
FROM (
    SELECT bank_tx_id
    FROM purchase_events
    WHERE event_date BETWEEN $1 AND $2

    UNION

    SELECT bank_tx_id
    FROM pending_purchases
    WHERE COALESCE(event_date, (created_at AT TIME ZONE 'America/Chicago')::date)
            BETWEEN $1 AND $2
) AS tracked
ORDER BY bank_tx_id ASC;
```

`UNION` (not `UNION ALL`) collapses confirm-path duplicates; explicit
`DISTINCT` makes intent obvious. No `mercury_category` filter — CubeSmart
storage rent counts as "HQ has seen this" for gap detection even though
it's excluded from COGS aggregation.

## Tests added

All three pass against the remote Windows-box test DB.

1. **empty period renders `[]` not `null`** — guards against `nil`-slice
   marshaling regression. Same pattern as the existing `by_vendor` test.
2. **all states present, deduped, sorted** — tx A in `purchase_events`,
   tx B unconfirmed pending, tx C discarded pending, tx D confirm-path
   (both tables). Asserts `["tx-A","tx-B","tx-C","tx-D"]` in order, and
   that an out-of-period sentinel does not leak in.
3. **period boundary uses `COALESCE(event_date, created_at::Chicago)`**
   — mirrors the existing pending-gate axis tests with four pending rows
   covering each (event_date, created_at) × (in, out) quadrant. Asserts
   only the rows whose effective period-date lands in window appear.
