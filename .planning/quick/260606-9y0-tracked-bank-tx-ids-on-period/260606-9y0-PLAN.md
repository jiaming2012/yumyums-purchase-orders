# Expose `tracked_bank_tx_ids` on `/period-summary`

## Problem

The `completeness.ready` gate on `GET /api/v1/inventory/period-summary`
only catches transactions HQ has already seen — either confirmed in
`purchase_events` or queued in `pending_purchases`. It cannot catch
transactions that Mercury knows about but the receipt worker hasn't
ingested yet. When sales-processor runs the weekly payroll PDF before
the receipt worker's next poll, food cost % is silently understated.

## Scope

Add a `tracked_bank_tx_ids` array to the `/period-summary` JSON response
containing every `bank_tx_id` HQ has touched for the period, across all
states (confirmed / pending / discarded). Sales-processor will diff this
against Mercury's own transaction list for the same period and
fail-fast on any gap.

Additive only — no schema change, no breaking response shape.

## Files

| File | Change |
|---|---|
| `backend/internal/inventory/types.go` | Add `TrackedBankTxIDs []string` field on `PeriodSummary` with json tag `tracked_bank_tx_ids`. |
| `backend/internal/inventory/handler.go` | Between step 3 (pending review IDs) and step 4 (unlinked line items): UNION of `bank_tx_id` from `purchase_events` (filter on `event_date BETWEEN`) and `pending_purchases` (filter on `COALESCE(event_date, (created_at AT TIME ZONE 'America/Chicago')::date) BETWEEN`). ORDER BY ASC. Scan into `[]string`. Wire into response struct as `TrackedBankTxIDs`. |
| `backend/internal/inventory/period_summary_test.go` | Subtests: empty period → `[]` not `null`; all states present and sorted; dedup on confirm path; period boundary uses the same COALESCE expression as the pending gate. |

## SQL

```sql
SELECT DISTINCT bank_tx_id
FROM (
    SELECT bank_tx_id
    FROM purchase_events
    WHERE event_date BETWEEN $1 AND $2

    UNION

    SELECT bank_tx_id
    FROM pending_purchases
    WHERE COALESCE(event_date, (created_at AT TIME ZONE 'America/Chicago')::date)
            BETWEEN $1 AND $2
) AS tracked
ORDER BY bank_tx_id ASC;
```

The COALESCE expression mirrors the pending-review filter shipped in
phase `260606-0gh` so both queries decide period membership the same way.

## Out of scope

- Sales-processor consumer (see `payroll-mercury-gap-check.md`).
- Any change to `completeness.ready`. The gate stays as-is; the new
  field is parallel detection.
- Filtering by `mercury_category`. This list is for completeness
  detection, not COGS aggregation — CubeSmart-category rows still count
  as "HQ has seen this".
