<objective>
Three bundled fixes for the receipt parsing pipeline (motivated by a real Restaurant Depot $391.96 PDF receipt that failed parsing with no visible reason):

1. **Persist parse_error.** When ParseReceipt fails (after the Sonnet fallback below), store the actual error string on `pending_purchases.parse_error`. The FE pending-review card surfaces a small italic muted line "Parser error: <first 140 chars>" so the owner can see WHY parsing failed.
2. **PDF iframe preview.** The view-receipt overlay currently uses `<img>` only — PDFs render as "Receipt image unavailable". Branch on `.pdf` and render an `<iframe>` instead, plus an "Open in new tab" link in the overlay header (iOS PWA's iframe PDF viewer is flaky — the link is the safety net).
3. **Sonnet fallback.** When Haiku ParseReceipt returns an error, retry once with `anthropic.ModelClaudeSonnet4_6` and `max_tokens=4096`. On Sonnet success, continue down the normal validate → createPurchaseEvent path. On Sonnet ALSO fail, route to pending review with `parse_error = "haiku: <haikuErr>; sonnet: <sonnetErr>"`.

Purpose: Without these, a PDF receipt is invisible in the UI and a parse failure is opaque — the owner can't diagnose or unstick the pipeline.
Output: Migration 0069, new parser variant + seam, threaded parseError parameter, JSON field on pending list response, FE pending card update + view-receipt iframe branch, 3 backend tests + 2 FE tests.
</objective>
