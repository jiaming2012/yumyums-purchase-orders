## Decisions Made

- **Sum-constraint architecture is bypass-resistant** — the 422 envelope is the contract Plan 05's `autoSaveRecipe` rollback messaging depends on. By enforcing the SUM check in the repository tx (Wave 1 contract) and translating `ErrSumExceeds100` to the 422 envelope in the handler, even a curl/future-tool client that bypasses the UI's local sum check gets the same 422. The TestCreateRecipe_SumExceeds100_NamesLargestSibling + TestUpdateRecipe_SumExceeds100_NamesSibling tests verify this end-to-end.
- **CreateRecipe excludeRecipeID = all-zeros UUID** — On 422, the rolled-back insert is gone from the DB. The "exclude this recipe id" parameter to `LargestSiblingAllocation` is therefore moot for the Create path; passing a sentinel zero-UUID returns the largest surviving sibling, which is the right thing to name. (For Update, we pass the actual recipeID so we don't accidentally point at ourselves.)
- **Default Chicago-week window** — When the frontend doesn't pass from/to (Plan 05 may forget on first render), the handler falls back to the last 7 days ending today in America/Chicago. Matches the D-20 drift scheduler tz convention. UTC fallback only if the TZ database is missing.
- **Unique-violation detection via error-string scan** — pgx v5 surfaces SQLSTATE 23505 inside the error message; the handler tolerates three string variants (`unique_violation`, `duplicate key`, `23505`) so a pgx upgrade can't silently break the 409 path.
- **No subgroup re-test** — `RecipeWithMenu.MenuSubgroup` is `*string`; the underlying SQL `SELECT mi.menu_subgroup` returns NULL by default in seedMenuItemFull. Existing repository tests cover the nullable path; not retested here.
