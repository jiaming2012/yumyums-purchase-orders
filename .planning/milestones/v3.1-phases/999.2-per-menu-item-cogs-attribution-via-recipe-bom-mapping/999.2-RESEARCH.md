# Phase 999.2: Per-menu-item COGS attribution via recipe/BOM mapping — Research

**Researched:** 2026-06-04
**Domain:** Go + Postgres backend (chi router, pgx pool) + vanilla HTML/CSS/JS frontend (no build step)
**Confidence:** HIGH

## Summary

Phase 999.2 adds three thin layers on top of a stack the codebase already exhibits:

1. A `recipes` join table (migration `0062`) that pairs `purchase_items.id` with `menu_items.id` and stores a rough `usage_pct`. The math, the constraints, and the FK cascade rules all follow patterns the repo has used since Phase 12 (inventory) and Phase 22 (Toast).
2. A service-token `GET /api/v1/inventory/menu-cogs` endpoint that is a direct sibling of Phase 21's `period-summary`. The Phase 21 handler is 126 lines (`handler.go:1064-1189`); `menu-cogs` will be the same shape with one extra CTE for the recipe allocation join, and an optional `?breakdown=true` branch.
3. A weekly Monday Chicago-time drift-check goroutine inside HQ that fires Cliq alerts via the existing `internal/alerts/Queue` and persists banner state in a new `drift_check_results` table (recommended) for the in-app banner.

The Recipes tab in `inventory.html` reuses the existing tabs/collapse/picker/merge patterns wholesale — the only **net-new component** is the slider (D-05), which is a styled `<input type="range" step="5">`. Everything else is CSS class-reuse and DOM idioms already in the file.

**Primary recommendation:** Treat this as a "copy Phase 21 + add SQL CTE + add migration + new package `internal/recipes/`" job. Put recipes in their own Go package (NOT inside `internal/inventory/` or `internal/toast/`) because it has its own bounded vocabulary (allocation %, drift) and the handler signature touches both `purchase_items` (inventory) and `menu_items` (toast) — keeping it separate avoids cross-package coupling in either direction. Reuse the Phase 21 PATTERNS.md analog map (handler factory, writeJSON/writeError, error envelope) verbatim.

## User Constraints (from CONTEXT.md)

### Locked Decisions (D-01 through D-22 — non-negotiable)

**Recipes Tab UX & Placement:**
- **D-01:** New sibling tab between Menu and Trends. Tab order becomes: `Purchases / Stock / Menu / Recipes / Trends / Cost / Setup` (t1..t7).
- **D-02:** Each ingredient row collapsed by default, tap to expand. Collapsed shows ingredient name + last-week spend + `Unallocated: X%`.
- **D-03:** `%` edits autosave on blur per row (`workflows.html` `autoSaveField` pattern). No save button. Server-side 422 (sum > 100) names the conflicting menu item and rolls back the edit.
- **D-04:** `+ Add menu item` opens fullscreen picker showing **all menu items, except those already allocated to this ingredient**. Items allocated to OTHER ingredients DO appear.
- **D-05:** `%` editor is a **slider with 5% snap points**. Net-new component.
- **D-06:** Read-only per-menu-item summary section below the ingredients list. Tap a menu item → shows its ingredients with % and $. Editing is always ingredient-first.
- **D-07:** When a Toast menu item disappears (rename/removal/no-sales), recipe rows **persist**. Drift check D-21 surfaces "menu items in recipes with no sales last week."
- **D-08:** Ingredient rows support a **merge** action for stale menu items (re-point FK to new `menu_items.id`). Mirrors vendor/item merge pattern.
- **D-09:** Toast permits multiple menu items with the same name in different menus. Picker AND read-only summary must show `menu_group` (and `menu_subgroup` when present).

**Cost Reference Price:**
- **D-10:** `ingredient_cost_per_unit` = window-sum of `purchase_line_items.quantity * price` within `[from..to]` per `purchase_item`. Same math basis as Phase 21's `cogs_excl_tax` for reconciliation.
- **D-11:** Tax-inclusive. Tax pro-rated per line: `line_total_incl_tax = (qty * price) * (event.total / event.subtotal)`.
- **D-12:** Any `purchase_items` row can be allocated — no `is_food` flag. Unallocated rows flow to `unallocated_cogs`.

**menu-cogs Endpoint Contract:**
- **D-13:** HQ is truth source for `units_sold`. Endpoint joins `recipes` → `menu_items` → `daily_menu_sales` internally.
- **D-14:** `GET /api/v1/inventory/menu-cogs?from=YYYY-MM-DD&to=YYYY-MM-DD` — exact mirror of Phase 21 contract. Same Bearer auth via `HQ_INVENTORY_SERVICE_TOKEN`, same 503-if-unset, idempotent and cacheable.
- **D-15:** No completeness gate field. Always returns 200 given valid dates + auth.
- **D-16:** Default response = summary only (one row per menu_item). `?breakdown=true` adds per-ingredient detail per menu item.
- **D-17:** `unallocated_cogs` shape: default = single number; with `?breakdown=true` = `{total, by_ingredient: [{purchase_item_description, amount, reason}]}`.
- **D-18:** Error envelope mirrors Phase 21 exactly (400/401/500/503).

**Drift Check Delivery:**
- **D-19:** Two channels — Zoho Cliq `purchaseandinventory` channel with deep link, plus persistent in-app banner on Recipes tab. No email digest.
- **D-20:** Weekly scheduled job in HQ — Monday morning Chicago time. Mirrors Phase 17 cutoff scheduler pattern. Once per week against prior week's data. NOT driven by the endpoint.
- **D-21:** Thresholds: **Unallocated > 10%** (SUM(usage_pct) < 90% AND >$0 spend last week), **Divergence > 20%** (configured vs. implied), **Zero-sales drift** (menu items in recipes with 0 units sold last week).
- **D-22:** No dismiss button on banner. Each Monday's run replaces banner content. Clean weeks → banner gone.

Data flow for `menu-cogs` summary mode (single SQL round trip):

```
purchase_line_items
   join purchase_events (window filter by event_date)
   group by purchase_item_id
   → window_spend[purchase_item_id]   (tax-inclusive via pro-ration)

recipes
   join menu_items (D-09: include menu_group)
   join daily_menu_sales (window filter by business_date)
   group by menu_item_id, purchase_item_id
   → sum_units_sold[menu_item_id], usage_pct[(menu_item, purchase_item)]

allocation per (menu_item, purchase_item):
   alloc_cost = window_spend[purchase_item] * (usage_pct / 100)
   alloc_per_unit = alloc_cost / sum_units_sold[menu_item]   (NULLIF guard)

unallocated per purchase_item:
   unalloc[purchase_item] = window_spend[purchase_item] * (1 - SUM(usage_pct)/100)
   total_unallocated = SUM(unalloc[*])
```

### Pattern 1: HTTP handler factory closing over `*pgxpool.Pool`

**What:** Every HTTP handler is a factory function that returns `http.HandlerFunc`, closing over the pool. Established universally in the repo.

**When to use:** All seven new HTTP handlers in `internal/recipes/handler.go`.

**Example (canonical shape from `handler.go:1064-1189` — the Phase 21 `PeriodSummaryHandler` that `MenuCogsHandler` will mirror):**

```go
    return func(w http.ResponseWriter, r *http.Request) {
        fromStr := r.URL.Query().Get("from")
        toStr := r.URL.Query().Get("to")

            return

            writeError(w, http.StatusBadRequest, "to must be YYYY-MM-DD")
            return
        }
        if fromStr > toStr {
            writeError(w, http.StatusBadRequest, "from must be <= to")
            return
        }
        breakdown := r.URL.Query().Get("breakdown") == "true"

        // ... CTE query (see §2 below) ...

        writeJSON(w, http.StatusOK, resp)
    }
}
```

The error envelope strings (`"from must be YYYY-MM-DD"`, `"from must be <= to"`, `"internal_error"`, `"unauthorized"`, `"service_token_not_configured"`) must match Phase 21 byte-for-byte per D-18.

```go
func writeJSON(w http.ResponseWriter, status int, v any) {
```

### Pattern 3: Background goroutine ticker (Phase 17 scheduler)

**What:** A `time.NewTicker` fires every 15 minutes; inside the tick, the function computes whether NOW falls within a target window (cutoff day-of-week + reminder window). If yes, do the work; otherwise return silently. Idempotent via DB `INSERT … ON CONFLICT DO NOTHING`.

**When to use:** Monday drift-check (D-20).

**Example (from `backend/internal/purchasing/scheduler.go:22-50`):**

```go
// Source: backend/internal/purchasing/scheduler.go [VERIFIED]
func StartScheduler(ctx context.Context, pool *pgxpool.Pool) {
    log.Println("cutoff scheduler: starting (15m tick)")
    go func() {
        runSchedulerTick(ctx, pool)  // run immediately on start
        ticker := time.NewTicker(15 * time.Minute)
        defer ticker.Stop()
        for {
            select {
            case <-ctx.Done():
                log.Println("cutoff scheduler: shutting down")
                return
            case <-ticker.C:
                runSchedulerTick(ctx, pool)
            }
        }
    }()
}
```

Adapt for drift: `recipes.StartDriftScheduler(ctx, pool)`. - **Adding new dependencies** — every line in this phase can be written with existing repo packages and the stdlib. Adding a slider library, a cron library, or a frontend framework breaks the no-build-step constraint.

## Common Pitfalls

### Pitfall 1: Lexicographic date compare assumes `YYYY-MM-DD` format

**What goes wrong:** Comparing `fromStr > toStr` only works because `YYYY-MM-DD` sorts naturally. If anyone "improves" the format to `MM/DD/YYYY` or `Jan 5 2026`, the comparison silently lies.
**Why it happens:** Easy to follow without realizing the implicit format constraint.
**How to avoid:** Keep the validation strict (`time.Parse("2006-01-02", s)` → 400 on parse error). Phase 21 does it exactly right (`handler.go:1068-1079`).
**Warning signs:** Tests with non-default date formats.

### Pitfall 2: `event_date` is `DATE` (no TZ) but `created_at` is `TIMESTAMPTZ`

**What goes wrong:** Mixing the two in a date-range filter without the TZ cast on `TIMESTAMPTZ` produces off-by-one-day errors at midnight Chicago time.
**Why it happens:** Postgres silently coerces, but the result depends on the server's TZ.
**How to avoid:** For `menu-cogs`, use `purchase_events.event_date BETWEEN $1 AND $2` (already a DATE — no cast). For drift check use `daily_menu_sales.business_date BETWEEN $1 AND $2` (also a DATE). **No `TIMESTAMPTZ` appears in the menu-cogs query path**, so this pitfall doesn't bite here — but flag it for the planner so they don't accidentally introduce a `recipes.updated_at` filter without the cast.
**Warning signs:** Any `created_at`-based filter without `AT TIME ZONE 'America/Chicago'`.

### Pitfall 3: `daily_menu_sales` may be incomplete (Toast outage)

**What goes wrong:** If the Toast ingest is degraded, `units_sold` for last week may be 0 for menu items that actually sold. This will fire false "zero-sales drift" alerts (D-21).
**Why it happens:** Phase 22.1 D-06 explicitly accepts that Spaces unreachable doesn't crash the server but drops a tick.
**How to avoid:** Before running drift check, verify at least N business dates in the prior week have rows in `daily_menu_sales`. If `< 5` of 7 days present, log "ingest stale — skipping drift check" and don't insert a drift result row (no banner, no Cliq). The CONTEXT.md "Claude's Discretion" flags this as a planner choice — recommend **suppress the run** (don't fire false alarms; rely on the existing toast-degraded Cliq alert to surface the upstream problem).
**Warning signs:** Days in `daily_menu_sales` for the target window < 5.

### Pitfall 4: `purchase_events.total` includes tax — `subtotal` is implicit

**What goes wrong:** Tax pro-rating per D-11 wants `(qty*price) * (event.total / event.subtotal)`. The schema has `total NUMERIC(10,2)` and `tax NUMERIC(10,2)` but **no `subtotal` column** (verified at `0024_inventory.sql:33-42`). Subtotal must be computed as `total - tax`.
**Why it happens:** Schema doesn't materialize subtotal because it's derivable.
**How to avoid:** SQL expression: `(pli.quantity * pli.price) * (pe.total / NULLIF(pe.total - pe.tax, 0))`. NULLIF guards the rare case where an event was entered with only tax (`subtotal = 0`); the pro-rating then NULLs out for that line, and a COALESCE outside falls back to the untaxed amount.
**Warning signs:** `subtotal` referenced anywhere in SQL without `pe.total - pe.tax`.

### Pitfall 5: `units_sold = 0` makes `cost / units` divide by zero

**What goes wrong:** For a menu item with recipe rows but no sales last week (D-07 persistence case), `ingredient_cost_per_unit = alloc_cost / 0` is undefined.
**Why it happens:** D-07 explicitly preserves recipe rows for menu items with no sales.
**How to avoid:** `NULLIF(SUM(dms.units_sold), 0)` in the division. Return `ingredient_cost_per_unit: null` in JSON when units = 0; sales-processor can render `—` for these. `ingredient_cost_total` should still be 0 (nothing was sold to attribute cost to). Document this in the SALES-PROCESSOR-CONTRACT.
**Warning signs:** Division without `NULLIF` guard.

### Pitfall 6: Slider `input` vs `change` event semantics

**What goes wrong:** `input` fires on every value change during drag (every pixel). `change` fires only on release. Calling `autoSaveRecipe` on `input` floods the server.
**Why it happens:** Easy to confuse if not specifically aware.
**How to avoid:** Per UI-SPEC Component 3, on `input` update the chip + running total ONLY (no API call). On `change` (release), call `autoSaveRecipe`. The native event names already enforce this if used correctly.
**Warning signs:** Network tab shows multiple PUT requests for one drag.

### Pitfall 7: 5%-snap with floating-point math

**What goes wrong:** Storing `usage_pct` as `NUMERIC(5,2)` is fine, but if the slider posts `45` and the server stores `45.00`, retrieval shows `45` not `45.00` in JSON. Conversely if the slider step is `step="5"` but somehow `5.0000001` slips through, the row violates the snap invariant.
**Why it happens:** Native `<input type="range" step="5">` returns integer strings when min/max are integers; safe. The risk is if anyone later adds float increments.
**How to avoid:** Server-side validation: `if usage_pct < 0 || usage_pct > 100 || int(usage_pct) % 5 != 0 { 422 }`. This makes the snap-point invariant explicit in the API, not just in the UI. NUMERIC(5,2) keeps the type wide enough for a future "fine-tune" mode without migration.
**Warning signs:** Any client other than the slider posting non-multiple-of-5 values.

### Pitfall 8: Concurrent slider edits create sum > 100 race

**What goes wrong:** Two browser tabs (or two crew members) move sliders for the same `purchase_item` simultaneously. Both pass the local sum check (current sum + their delta ≤ 100), but their combined writes push the total above 100.
**Why it happens:** Optimistic UI without server-side serialization.
**How to avoid:** Server-side: wrap the check + the UPDATE in `BEGIN; ... COMMIT;` and use `SELECT … FOR UPDATE` on the existing recipe row, OR use a single atomic UPDATE that returns the new SUM via `RETURNING` and a `CHECK` constraint at row level. Recommended approach (simplest): in the PUT handler:

```sql
WITH proposed AS (
  UPDATE recipes SET usage_pct = $1 WHERE id = $2 RETURNING purchase_item_id
)
SELECT SUM(usage_pct) FROM recipes WHERE purchase_item_id = (SELECT purchase_item_id FROM proposed);
```

…all inside one transaction. If sum > 100, rollback and return 422. (Or use a deferred CHECK constraint — see §1.)

**Warning signs:** Tests that simulate two clients writing simultaneously.

### Migration shape — DDL for `0062_recipes.sql`

```sql
-- Source pattern: backend/internal/db/migrations/0060_menu_items.sql + 0061_daily_menu_sales.sql [VERIFIED]
-- +goose Up
BEGIN;

CREATE TABLE recipes (
  id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  menu_item_id     UUID NOT NULL REFERENCES menu_items(id)    ON DELETE CASCADE,
  purchase_item_id UUID NOT NULL REFERENCES purchase_items(id) ON DELETE CASCADE,
  usage_pct        NUMERIC(5,2) NOT NULL CHECK (usage_pct >= 0 AND usage_pct <= 100),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (menu_item_id, purchase_item_id)
);

-- Index strategy (planner decision — recommendation):
--
-- The menu-cogs query path:
--   recipes → menu_items (PK lookup, no index needed beyond unique pair)
--   recipes → purchase_items (FK lookup for spend aggregation per purchase_item)
--   purchase_line_items (filter by event_date via join) grouped by purchase_item_id
--   daily_menu_sales (filter by business_date) grouped by menu_item_id
--
-- The unique constraint (menu_item_id, purchase_item_id) creates a btree index that
-- serves BOTH FK directions when prefixed. For the menu_item-first scans (the
-- "list recipes for this menu item" query the read-only summary uses, and the
-- drift check), this index is sufficient.
--
-- For purchase_item-first scans (the per-ingredient SUM(usage_pct) check on every
-- PUT — Pitfall 8), we need a second index leading with purchase_item_id:
CREATE INDEX recipes_purchase_item_id_idx ON recipes(purchase_item_id);

-- updated_at: no trigger needed — server sets it explicitly on every UPDATE.
-- This matches the convention of menu_items (no trigger, updated externally
-- by the ingest worker per 0060_menu_items.sql).

COMMIT;

-- +goose Down
BEGIN;
DROP TABLE IF EXISTS recipes;
COMMIT;
```

**Cascade rationale (planner-locked recommendation):**
- `menu_items.id ON DELETE CASCADE` — if Toast hard-deletes a menu item, the recipe row is orphaned and should drop. D-07 covers the *normal* "no sales" / "renamed" case where `menu_items` rows persist (only `last_seen` ages). Toast hard-deletion is rare but possible and unrecoverable; cascade is the right behavior.
- `purchase_items.id ON DELETE CASCADE` — `purchase_items` already cascades from `item_groups` (`group_id ON DELETE SET NULL`), but the row itself is rarely deleted (merge re-points instead). Cascade here is defensive for the same rare-but-unrecoverable case.

**Why NOT a trigger for `updated_at`:** Phase 22 `menu_items` doesn't use a trigger (it's set by the ingest writer). Same convention here — server-side handler sets `updated_at = now()` on every UPDATE. Keeps the schema simple and auditable.

### menu-cogs SQL (summary mode — the canonical CTE)

```sql
-- Source pattern: backend/internal/inventory/handler.go:1088-1103 (Phase 21 CTE) [VERIFIED]
-- Adapted for menu-cogs per D-10, D-11, D-13, D-16, D-17.

WITH
-- 1) Window spend per purchase_item, tax-inclusive (D-11 pro-rating).
window_spend AS (
  SELECT
    pli.purchase_item_id,
    SUM(
      (pli.quantity * pli.price) *
      COALESCE(pe.total / NULLIF(pe.total - pe.tax, 0), 1)
    ) AS spend_incl_tax
  FROM purchase_line_items pli
  JOIN purchase_events pe ON pe.id = pli.purchase_event_id
  WHERE pe.event_date BETWEEN $1 AND $2
    AND pli.purchase_item_id IS NOT NULL  -- unlinked rows flow only to period-summary
  GROUP BY pli.purchase_item_id
),
-- 2) Sum of usage_pct per purchase_item — used for the unallocated residual.
purchase_item_alloc AS (
  SELECT
    purchase_item_id,
    COALESCE(SUM(usage_pct), 0) AS sum_pct
  FROM recipes
  GROUP BY purchase_item_id
),
-- 3) Per-menu-item units sold in the window (D-13: HQ owns this).
menu_units AS (
  SELECT
    dms.menu_item_id,
    SUM(dms.units_sold) AS units_sold
  FROM daily_menu_sales dms
  WHERE dms.business_date BETWEEN $1 AND $2
  GROUP BY dms.menu_item_id
),
-- 4) Cost allocation per (menu_item, purchase_item): spend × (pct/100).
alloc AS (
  SELECT
    r.menu_item_id,
    r.purchase_item_id,
    r.usage_pct,
    COALESCE(ws.spend_incl_tax, 0) * (r.usage_pct / 100.0) AS alloc_cost
  FROM recipes r
  LEFT JOIN window_spend ws ON ws.purchase_item_id = r.purchase_item_id
)
-- 5) Final summary: per menu_item, with units_sold and ingredient_cost_total.
SELECT
  mi.id::text                   AS menu_item_id,
  mi.master_id                  AS toast_master_id,
  mi.name                       AS menu_item_name,
  mi.menu_group                 AS menu_group,
  mi.menu_subgroup              AS menu_subgroup,
  COALESCE(mu.units_sold, 0)    AS units_sold,
  ROUND(COALESCE(SUM(a.alloc_cost), 0)::numeric, 2) AS ingredient_cost_total,
  CASE
    WHEN COALESCE(mu.units_sold, 0) = 0 THEN NULL
    ELSE ROUND((COALESCE(SUM(a.alloc_cost), 0) / mu.units_sold)::numeric, 4)
  END AS ingredient_cost_per_unit
FROM menu_items mi
JOIN alloc a ON a.menu_item_id = mi.id   -- only menu items with recipes appear
LEFT JOIN menu_units mu ON mu.menu_item_id = mi.id
GROUP BY mi.id, mi.master_id, mi.name, mi.menu_group, mi.menu_subgroup, mu.units_sold
ORDER BY mi.name;

-- Second query (same handler call), for the unallocated_cogs total:
SELECT ROUND(COALESCE(SUM(
  ws.spend_incl_tax * (1 - COALESCE(pia.sum_pct, 0) / 100.0)
), 0)::numeric, 2) AS unallocated_cogs
FROM window_spend ws
LEFT JOIN purchase_item_alloc pia ON pia.purchase_item_id = ws.purchase_item_id;
```

**With `?breakdown=true`:** add `alloc.purchase_item_id`, `pi.description AS purchase_item_description`, and `alloc.usage_pct` to the SELECT (remove the GROUP BY), and build a per-menu-item ingredients array in Go. For the unallocated breakdown, add a third query:

```sql
SELECT
  pi.description                                                   AS purchase_item_description,
  ROUND((ws.spend_incl_tax * (1 - COALESCE(pia.sum_pct, 0) / 100.0))::numeric, 2) AS amount,
  CASE
    WHEN COALESCE(pia.sum_pct, 0) = 0   THEN 'no recipe'
    WHEN COALESCE(pia.sum_pct, 0) < 100 THEN 'partial allocation (' || pia.sum_pct || '%)'
    ELSE NULL
  END                                                              AS reason
FROM window_spend ws
JOIN purchase_items pi ON pi.id = ws.purchase_item_id
LEFT JOIN purchase_item_alloc pia ON pia.purchase_item_id = ws.purchase_item_id
WHERE COALESCE(pia.sum_pct, 0) < 100   -- only include items with unallocated dollars
ORDER BY amount DESC;
```

**Round-trip cost:** 2 queries for summary mode, 3 for breakdown mode. All can share the same `window_spend` / `purchase_item_alloc` CTEs by combining into a single SQL statement using `WITH ... SELECT ... UNION ALL SELECT ...` — but the cleanest Go shape is to run them sequentially in one handler invocation, mirroring Phase 21's 3-query pattern. CTEs being re-computed per query is fine at this scale (`menu_items` is in the hundreds, `recipes` in the low thousands).

```go
var purchaseItemID string
err = tx.QueryRow(r.Context(),
    `UPDATE recipes SET usage_pct = $1, updated_at = now()
     WHERE id = $2
     RETURNING purchase_item_id`, input.UsagePct, recipeID,
).Scan(&purchaseItemID)
if err != nil {
    if err == pgx.ErrNoRows {
        writeError(w, http.StatusNotFound, "recipe_not_found"); return
    }
    writeError(w, http.StatusInternalServerError, "internal_error"); return
}

// Re-compute the SUM after the update, INSIDE the tx.
var newSum float64
err = tx.QueryRow(r.Context(),
    `SELECT COALESCE(SUM(usage_pct), 0) FROM recipes WHERE purchase_item_id = $1`,
    purchaseItemID,
).Scan(&newSum)
if err != nil {
    writeError(w, http.StatusInternalServerError, "internal_error"); return
}
if newSum > 100 {
    // Find the largest sibling allocation to name in the 422 message.
    var conflictMenu string
    var conflictPct float64
    _ = tx.QueryRow(r.Context(),
        `SELECT mi.name, r.usage_pct
         FROM recipes r JOIN menu_items mi ON mi.id = r.menu_item_id
         WHERE r.purchase_item_id = $1 AND r.id != $2
         ORDER BY r.usage_pct DESC LIMIT 1`,
        purchaseItemID, recipeID,
    ).Scan(&conflictMenu, &conflictPct)
    // Rollback (defer fires); return 422.
    writeJSON(w, http.StatusUnprocessableEntity, map[string]any{
        "error":              "sum_exceeds_100",
        "conflict_menu_item": conflictMenu,
        "conflict_pct":       conflictPct,
    })
    return
}
if err := tx.Commit(r.Context()); err != nil {
    writeError(w, http.StatusInternalServerError, "internal_error"); return
}
w.WriteHeader(http.StatusNoContent)
```

**422 envelope shape — recommendation:** `{"error": "sum_exceeds_100", "conflict_menu_item": "<name>", "conflict_pct": <number>}`. Reasoning: the existing Phase 21 envelope is `{"error": "..."}` — single string. For a useful 422 the UI needs to name the conflicting item (per CONTEXT.md D-03), so structured fields are warranted. The `error` key stays a single sentinel string ("sum_exceeds_100"); supplementary fields carry the detail. This deviates slightly from Phase 21's pure single-field envelope but is consistent with how richer errors are typically extended (Phase 21 doesn't have a 422 case to compare against, so this is the new precedent).

### Drift scheduler structure (Monday window-match)

```go
// Source pattern: backend/internal/purchasing/scheduler.go:22-50 + 165-243 [VERIFIED]
// Adapted for weekly Monday check (D-20) with 15m polling granularity.

package recipes

func StartDriftScheduler(ctx context.Context, pool *pgxpool.Pool) {
    log.Println("recipes drift scheduler: starting (15m tick, fires Monday 09:00 America/Chicago)")
    go func() {
        runDriftTick(ctx, pool)  // immediate at boot
        ticker := time.NewTicker(15 * time.Minute)
        defer ticker.Stop()
        for {
            select {
            case <-ctx.Done():
                log.Println("recipes drift scheduler: shutting down")
                return
            case <-ticker.C:
                runDriftTick(ctx, pool)
            }
        }
    }()
}

func runDriftTick(ctx context.Context, pool *pgxpool.Pool) {
    loc, err := time.LoadLocation("America/Chicago")
    if err != nil { log.Printf("drift: TZ load: %v", err); return }
    now := time.Now().In(loc)
    // Monday morning window: 09:00–09:14 Chicago time on Monday.
    if now.Weekday() != time.Monday || now.Hour() != 9 || now.Minute() >= 15 {
        return
    }

    // Compute target week_start (this Monday at 00:00 Chicago — the date for which we ARE running).
    weekStart := time.Date(now.Year(), now.Month(), now.Day(), 0, 0, 0, 0, loc)
    weekStartStr := weekStart.Format("2006-01-02")

    // Idempotency: if drift_check_results already has this week, return.
    var exists bool
    err = pool.QueryRow(ctx,
        `SELECT EXISTS(SELECT 1 FROM drift_check_results WHERE week_start = $1)`,
        weekStartStr,
    ).Scan(&exists)
    if err != nil { log.Printf("drift: idempotency check: %v", err); return }
    if exists { return }

    // Compute drift against PRIOR week: [weekStart - 7d, weekStart - 1d].
    priorFrom := weekStart.AddDate(0, 0, -7).Format("2006-01-02")
    priorTo   := weekStart.AddDate(0, 0, -1).Format("2006-01-02")

    // (Optional Pitfall 3 guard: check daily_menu_sales completeness for [priorFrom..priorTo].
    // If < 5 of 7 days have rows, log "ingest stale — skipping drift check" and return WITHOUT inserting.)

    result, err := computeDrift(ctx, pool, priorFrom, priorTo)
    if err != nil { log.Printf("drift: compute: %v", err); return }

    payload, _ := json.Marshal(result)
    _, err = pool.Exec(ctx,
        `INSERT INTO drift_check_results (week_start, payload, created_at)
         VALUES ($1, $2, now())
         ON CONFLICT (week_start) DO NOTHING`,
        weekStartStr, payload,
    )
    if err != nil { log.Printf("drift: insert result: %v", err); return }

    // Fire Cliq alert if any drift was flagged.
    if result.HasDrift() {
        if alertQueue != nil {
            baseURL := os.Getenv("BASE_URL")
            if baseURL == "" { baseURL = "https://hq.yumyums.kitchen" }
            msg := formatCliqMessage(result, weekStartStr, baseURL)
            alertQueue.Enqueue(alerts.Alert{
                Channel: alerts.ChannelZohoCliq,
                Subject: "Recipes drift",
                Message: msg,
            })
        } else {
            log.Println("recipes drift scheduler: alertQueue not configured — banner only")
        }
    }
    log.Printf("recipes drift scheduler: week %s — %d flagged", weekStartStr, result.TotalFlagged())
}
```

## Open Questions

These are NOT decisions to re-debate — they're items the planner should explicitly resolve before generating tasks:

1. **Should `recipes` CRUD endpoints be admin-only or any-authenticated-user?**
   - What we know: CONTEXT.md doesn't restrict. UI-SPEC implies any user with Recipes tab access can edit.
   - What's unclear: Phase 17 / Phase 21 show patterns for both; e.g., `purchase_orders` admin-only routes use a separate middleware.
   - Recommendation: Default to any-authenticated. Owner can introduce role gating in a future quick task if it becomes noisy.

2. **Where does the in-app drift banner data come from on the front end?**
   - What we know: UI-SPEC Open Question 1 recommends a separate `GET /api/v1/inventory/recipes/drift` endpoint (read once per tab load).
   - What's unclear: Could embed in the `GET /recipes` list response.
   - Recommendation: separate endpoint per UI-SPEC. Cleaner, cacheable independently.

3. **Should the slider release with value=0 DELETE the row or PUT with usage_pct=0?**
   - What we know: UI-SPEC Open Question 2 recommends DELETE.
   - What's unclear: PUT-with-zero leaves a "zombie" row for future debugging context. DELETE simplifies the sum-constraint logic and the read-only summary.
   - Recommendation: DELETE the row. The Recipes tab is the source of truth — absence of a recipe IS the "0% allocation" semantic.

4. **Cache-Control headers on `menu-cogs`?**
   - What we know: CONTEXT.md "Claude's Discretion." Window is by definition immutable past `to`.
   - Recommendation: `Cache-Control: private, max-age=3600` (1h). Sales-processor calls it once per weekly run; HQ owner could refresh via curl. Phase 21 doesn't set this — and 1h is conservative enough that drift checks running between calls don't matter (drift is a separate signal).

5. **`drift_check_results` schema — recommend the planner add migration `0063` with this shape:**
   ```sql
   CREATE TABLE drift_check_results (
     week_start  DATE PRIMARY KEY,            -- the Monday the check ran for
     payload     JSONB NOT NULL,              -- the structured banner data (sections + items)
     created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
   );
   ```
   Keeping payload as JSONB matches the flexible-schema pattern already used by `workflows`. Banner endpoint = `SELECT payload FROM drift_check_results ORDER BY week_start DESC LIMIT 1`.
