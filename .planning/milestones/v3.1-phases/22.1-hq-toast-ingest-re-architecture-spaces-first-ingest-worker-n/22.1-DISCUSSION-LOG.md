## Spaces key layout & file naming

### Q1: What key prefix in the hq.yumyums bucket?

| Option | Description | Selected |
|--------|-------------|----------|
| `toast/YYYYMMDD/<file>` | Flat-ish, partitioned by business date. Simplest. Recommended — matches sales-processor's existing directory shape, easy to list/glob a date range. | ✓ |
| `toast/raw/YYYYMMDD/<file>` | Reserves toast/processed/, toast/exports/ etc. for future use. More future-proof if Phase 999.2 adds derived artifacts. | |
| `toast-ingest/<YYYY>/<MM>/<DD>/<file>` | Dedicated top-level prefix + deeper year/month/day nesting. Helps with lifecycle policies per-year. More keys to list. | |

**User's choice:** `toast/YYYYMMDD/<file>` → CONTEXT.md D-02

### Q2: What filename inside each date prefix?

| Option | Description | Selected |
|--------|-------------|----------|
| `ItemSelectionDetails.csv` (canonical) | Normalize on upload — strip Toast's `113866_HQ_YYYYMMDD_` prefix. Sync writer always uses this name. Recommended. | |
| Preserve Toast's original name | `113866_HQ_YYYYMMDD_ItemSelectionDetails.csv` as-is. Auditable, but ingest reader needs to construct the name including export_id. | |
| Both — canonical name + `.meta.json` sidecar | `ItemSelectionDetails.csv` as data + sidecar with original Toast filename, downloaded_at, source. Most metadata, more code. | ✓ |

**User's choice:** Both — canonical name + `.meta.json` sidecar → CONTEXT.md D-03

## Sync vs ingest worker structure

### Q3: How should the sync (SFTP→Spaces) and ingest (Spaces→DB) workers be wired?

| Option | Description | Selected |
|--------|-------------|----------|
| One combined worker, per-tick sync then ingest | Every 12h tick: sync each date if not in Spaces; then parse from Spaces → upsert DB. Single goroutine, single cadence. Recommended. | ✓ |
| Two separate workers, independent schedules | ToastSyncWorker on its own cadence (e.g. hourly) + ToastIngestWorker every 12h. Decouples backfill catch-up from menu-tab freshness. | |
| Sync as CLI/cron only; ingest as worker | No in-process sync. `cmd/sync-toast` becomes cron-driven utility. In-process worker reads Spaces only. | |

**User's choice:** One combined worker, per-tick sync then ingest → CONTEXT.md D-04

### Q4: When SFTP returns 'file does not exist' for a date in the sync path, what should happen?

| Option | Description | Selected |
|--------|-------------|----------|
| Graceful skip + INFO log (recommended) | `toast sync: skip YYYYMMDD (not in SFTP)` and continue. Expected case for older purged dates. Migration CLI fills these gaps. | ✓ |
| Skip silently when date older than 14 days, ERROR when recent | Recent misses indicate Toast publishing delays or auth broken. Older misses are expected. Tiered logging. | |
| Always ERROR + Zoho Cliq alert | Treat every miss as worth knowing. High noise once past Toast retention horizon. | |

**User's choice:** Graceful skip + INFO log → CONTEXT.md D-05

### Q5: If DO Spaces is unreachable during ingest, fail-fast like SFTP was, or graceful skip?

| Option | Description | Selected |
|--------|-------------|----------|
| Fail-fast (mirror Phase 22 D-12) | Log ERROR and exit the server. Spaces is core infra — if down, much else is broken. | |
| Graceful skip the tick, retry next cycle | Log ERROR but server keeps running. Auto-recovers when Spaces returns. | |
| Skip tick + Zoho Cliq alert after N consecutive failures | Graceful skip + Cliq message after 3 consecutive failed ticks (~36h). | ✓ |

**User's choice:** Skip tick + Zoho Cliq alert after N consecutive failures → CONTEXT.md D-06 (modifies Phase 22 D-12)

## Migration CLI scope & idempotency

### Q6: How should the migration CLI handle keys that already exist in Spaces?

| Option | Description | Selected |
|--------|-------------|----------|
| Skip if Spaces key exists (default), `--overwrite` flag for force | Safe re-run; --overwrite is opt-in. Recommended. | ✓ |
| Always upload (last-write-wins on Spaces) | Simpler code, costs bandwidth + Spaces PUT charges on re-runs. | |
| Compare local sha256 vs Spaces ETag, skip if same | Most correct, extra HEAD per key. Worth it if archive files may have been edited. | |

**User's choice:** Skip if Spaces key exists (default), `--overwrite` flag for force → CONTEXT.md D-09

### Q7: What does the migration CLI do beyond upload?

| Option | Description | Selected |
|--------|-------------|----------|
| Upload only — next ingest tick picks them up | Lean. Single ingest code path. Recommended. | ✓ |
| Upload + trigger immediate ingest of uploaded dates | After upload, CLI calls `toast.RunIngest` so DB is populated when CLI exits. | |
| Upload + ingest + dry-run/diff mode | Adds `--dry-run` and `--diff`. Heavier CLI, more knobs. | |

**User's choice:** Upload only — next ingest tick picks them up → CONTEXT.md D-10

### Q8: Source location flag and default for the migration CLI?

| Option | Description | Selected |
|--------|-------------|----------|
| `--source` flag, required, no default | Forces operator to specify path. Explicit. Recommended for one-shot tool. | ✓ |
| `--source` flag with sales-processor default | Defaults to `../sales-processor/output/toast_reports`. Convenient but encodes cross-repo layout in HQ. | |
| Read `SALES_PROCESSOR_ARCHIVE` env var, fail if unset | Env-driven. Adds another env var for a one-time tool. | |

**User's choice:** `--source` flag, required, no default → CONTEXT.md D-08

## Local cache policy

### Q9: Cache read flow during ingest?

| Option | Description | Selected |
|--------|-------------|----------|
| Cache-first: read local if present, else fetch Spaces → write cache | Cuts Spaces bandwidth on restart. Recommended. | |
| Always fetch Spaces, write cache for inspection only | Cache is debugging aid, not perf optimization. Simpler invariant (Spaces is always source of truth) but more bandwidth. | ✓ |
| Cache-first with stale-revalidate for rolling 7-day window | For dates in late-correction window, re-fetch Spaces; older dates hit cache. Most correct, slightly more code. | |

**User's choice:** Always fetch Spaces, write cache for inspection only → CONTEXT.md D-13

### Q10: Cache write flow during sync (when SFTP→Spaces succeeds)?

| Option | Description | Selected |
|--------|-------------|----------|
| Write cache alongside Spaces (same bytes, same tick) | On successful SFTP download: write cache AND upload Spaces. Recommended. | ✓ |
| Skip cache write — let ingest read populate it from Spaces | Sync only touches Spaces. Causes extra Spaces read per file per restart. | |

**User's choice:** Write cache alongside Spaces (same bytes, same tick) → CONTEXT.md D-14

### Q11: Cache eviction / size cap?

| Option | Description | Selected |
|--------|-------------|----------|
| No eviction — 365 days of CSVs ~365 MB worst case, fits on disk | Trivial size. Skip complexity. Recommended for v1. | ✓ |
| Age-based: drop dates older than 365 days on each tick | Simple LRU-by-date. Cheap to implement. | |
| Size cap: 1GB total, evict oldest | Most flexible. Requires walking cache dir + computing total size each tick. Overkill v1. | |

**User's choice:** No eviction → CONTEXT.md D-15
