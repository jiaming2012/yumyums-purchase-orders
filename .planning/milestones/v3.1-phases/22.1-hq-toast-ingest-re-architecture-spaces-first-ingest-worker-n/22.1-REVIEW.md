# Phase 22.1: Code Review Report

**Reviewed:** 2026-06-03T13:35:10Z
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Phase 22.1 re-architects the Toast ingest pipeline to a Spaces-first model: the worker
syncs SFTP → DO Spaces + local cache per date, then RunIngest reads CSVs back from
Spaces and upserts into Postgres. The migration CLI seeds the bucket from a sales-
processor archive. A consecutive-failure counter dispatches a single Cliq alert at
3 ticks.

The design is sound — clean separation between sync and ingest, single ingest code
path for live + replay + migration, graceful degradation when Spaces is unreachable,
and good adherence to the documented decisions (D-04/D-05/D-06/D-12/D-13/D-14).

That said, several concerns are worth addressing before this rides in production:

1. **`cache ⊆ Spaces` invariant has a window where it's violated** — if `os.Remove`
   fails after a failed PutObject, the cache file persists despite Spaces missing
   the key. Low likelihood but worth a tiny refactor (write cache LAST or upload
   to Spaces first).
2. **`SetAlertQueue` and the `consecSpacesFails` / `alertFiredAtThreshold` package
   globals are touched by goroutines without synchronization.** Today there's
   exactly one worker goroutine and one boot caller, so it works in practice —
   but the comment "single-worker assumption — no mutex needed" only holds for
   the failure counters; `SetAlertQueue` itself is a data race under Go's memory
   model (write at boot, read on each cycle from another goroutine, no
   synchronizes-with edge if boot doesn't happen-before goroutine start in some
   re-entry scenario).
3. **Migration CLI partial-failure semantics**: when CSV upload succeeds but the
   sidecar marshal/PutObject fails, the operator sees a `WARN` and the run keeps
   going — but the CSV is now in Spaces with no sidecar. The next run *without*
   `--overwrite` will skip that date entirely (HeadObject sees the CSV), so the
   sidecar gap is sticky. Either re-upload sidecar on skip, or expose a
   `--sidecar-only` mode.
4. **`runCycle` cold-start window can be enormous on a fresh DB.** A 90-day SFTP
   poll on every restart that hits an empty table is going to attempt 90
   SFTP dial cycles (and each `SyncDate` reads the private key from disk + opens
   a brand new SSH connection). Probably fine for one-shot bootstrap, but if
   the cold-start condition flaps (e.g., someone TRUNCATEs daily_menu_sales),
   the worker will hammer SFTP for ~36 minutes (90 dates × ~24s of timeouts
   worst case) and may breach Toast's connection limit.
5. **`HostKeyCallback` is `nil`-equivalent across the package** — inherited from
   sales-processor, documented, and out of scope for this phase, but flagging
   for completeness since this touches SFTP credential handling.

No critical security issues. No hardcoded secrets. No injection vectors. SQL is
parameterized. Logged secrets reviewed — none leak into log lines.

## Warnings

### WR-01: `cache ⊆ Spaces` invariant violated when `os.Remove` fails

**File:** `backend/internal/toast/sync.go:80-90`
**Issue:** The atomicity contract documented at the top of `SyncDate` ("cache ⊆ Spaces")
relies on `_ = os.Remove(cachePath)` succeeding when the Spaces upload fails. The
`_` swallows the error. On a busy filesystem, a permissions hiccup, or any race
with `migrate-toast-archive` running concurrently against the same cache dir,
the cache file persists while Spaces never received the object. Subsequent
`RunIngest` calls (which only read from Spaces — D-13) will skip the date, but
operators inspecting the cache (the explicit forensic-only purpose per D-12)
will be misled into thinking the date is durably archived.

**Fix:** Either invert the order (upload to Spaces first, then write cache only
on success — eliminates the cleanup branch entirely), or log the cleanup failure
loudly so it shows up in monitoring:

```go
if _, err := cfg.SpacesClient.PutObject(ctx, &s3.PutObjectInput{
    Bucket:      aws.String(cfg.SpacesBucket),
    Key:         aws.String(csvKey),
    Body:        bytes.NewReader(csvBytes),
    ContentType: aws.String("text/csv"),
}); err != nil {
    if rmErr := os.Remove(cachePath); rmErr != nil && !os.IsNotExist(rmErr) {
        log.Printf("ERROR toast sync: %s spaces upload failed AND cache cleanup failed: spaces=%v cleanup=%v — manual cleanup of %s required",
            dateDir, err, rmErr, cachePath)
    }
    return false, fmt.Errorf("toast sync: put %s: %w", csvKey, err)
}
```

The simpler refactor (upload to Spaces first) is preferred — it makes the
invariant a property of the code, not a property of cleanup-eventually-succeeding.

### WR-02: `SetAlertQueue` writes a package-global from boot, read from worker goroutine — no happens-before guarantee

**File:** `backend/internal/toast/worker.go:17-23, 175-186`
**Issue:** `alertQueue *alerts.Queue` is set by `SetAlertQueue` (called from
`cmd/server/main.go:546`) and read by `fireDegradedAlert` running inside the
goroutine spawned by `StartWorker`. The comment on line 28-29 says "Single-
worker assumption — no mutex needed (only runCycle reads/writes it, and
runCycle is invoked serially by the ticker)." That comment is correct for
`consecSpacesFails` and `alertFiredAtThreshold` (writer = worker goroutine,
reader = same goroutine).

But it does NOT apply to `alertQueue`: the writer is the main goroutine at boot,
the reader is the worker goroutine on every tick. In `cmd/server/main.go`,
`SetAlertQueue(alertQ)` is called at line 546, and `StartWorker` is called at
line 551 — so `go` happens-before the goroutine body and the write is visible.
In practice this works today.

The hazard is durability: any future refactor that calls `SetAlertQueue` AFTER
`StartWorker` (e.g., test setup, hot reload, a second wiring path) would
introduce a true data race with no compiler warning. Go's race detector will
catch it, but only if tests exercise it.

**Fix:** Either use `sync/atomic.Pointer[alerts.Queue]`, or document the
ordering invariant in `SetAlertQueue`'s godoc explicitly (the current doc says
"Call once at startup BEFORE StartWorker" — make it a hard requirement comment
that any reviewer would catch). Minimum:

```go
// SetAlertQueue wires the Cliq alert delivery queue into the toast worker.
//
// CONCURRENCY: Must be called from the main goroutine BEFORE StartWorker.
// Writes to this package-level variable are not synchronized; calling
// SetAlertQueue after StartWorker is a data race.
func SetAlertQueue(q *alerts.Queue) {
    alertQueue = q
}
```

Better: convert to atomic pointer so the API is misuse-resistant.

### WR-03: Cold-start backfill stampedes SFTP if `daily_menu_sales` is ever truncated

**File:** `backend/internal/toast/worker.go:94-105`, `backend/internal/toast/sync.go:46-69`
**Issue:** `isColdStart` returns `true` whenever `daily_menu_sales` is empty.
`runCycle` then sets `windowDays = cfg.BackfillDays` (90). The sync loop in
`runCycle` calls `SyncDate` for each of the 90 dates serially. Each `SyncDate`
opens a brand-new SSH connection via `dialWithRetry`, which uses a fresh
`os.ReadFile(cfg.SFTPKeyPath)` and `New(SFTPConfig{...})` per date — no
connection reuse. On the cold-start path against a Toast SFTP that only
retains ~14 days, most of those 90 dials will return a Download error,
which is interpreted as `ErrSFTPMiss` and skipped. That's correct, but it
means:

- 90 sequential SSH handshakes per tick on cold start
- If dial succeeds but Download fails for older dates: still 90 fresh
  connections
- Worst case (SFTP dial timeouts): 90 × 3 attempts × {5s,15s,30s} sleep
  between = ~75 minutes of sleeps per tick (plus dial timeouts)
- Cold start re-detects on every TRUNCATE of `daily_menu_sales`

The first tick on a real fresh install is fine — operators expect a slow
bootstrap. The hidden risk: if anyone re-seeds the table or runs
`DELETE FROM daily_menu_sales` for any reason, the next tick goes into
backfill mode without warning, with no rate limit, and may breach Toast's
connection limit (Toast's AWS Transfer Family endpoint has per-user
concurrent connection caps).

**Fix:**
1. Cache an SSH session within a single `runCycle` rather than dialing
   per-date. Currently each `SyncDate` call dials independently.
2. Add a guard rail: if backfill window > 14 days, log a one-line warning
   "toast worker: cold-start backfill — this will be slow, expect N SFTP
   dials" and consider a configurable upper bound.
3. Optional: emit a Cliq alert (not warn) on cold-start activation, since
   that is rare and significant.

```go
func runCycle(ctx context.Context, cfg Config) {
    cold, err := isColdStart(ctx, cfg.Pool)
    // ...
    if cold {
        log.Printf("toast worker: COLD START — %d-day backfill will dial SFTP %d times",
            cfg.BackfillDays, cfg.BackfillDays)
        // ... consider single shared client across SyncDate calls
    }
}
```

A connection-reuse refactor would be ideal but is larger; at minimum the
warning + reviewing the SSH-per-date pattern in a follow-up phase is
recommended.

### WR-04: Migration CLI leaves dates with CSV but no sidecar — sticky gap

**File:** `backend/cmd/migrate-toast-archive/main.go:161-175`
**Issue:** After a successful CSV `PutObject`, the sidecar is marshaled and
uploaded. If marshal fails or sidecar PutObject fails, both branches log
`WARN` and `continue`. On the next migration run *without* `--overwrite`,
`SpacesKeyExists(csvKey)` returns true (line 129-138) and the entire date
is skipped — including its missing sidecar. So a transient sidecar upload
failure is permanent until someone manually re-runs with `--overwrite`
(which re-uploads the CSV too, wasting bandwidth and bumping any "uploaded
at" timestamp if it were ever added).

This is a quality issue, not a correctness one (the ingest path doesn't
read sidecars — D-03 documents them as operational metadata only). But the
stated purpose of the sidecar is "operators can still distinguish live vs
migrated objects after the fact" (line 159-160), and that distinction is
silently lost.

**Fix:** Either (a) split the idempotency check to also verify
`SpacesKeyExists(metaKey)`, re-uploading just the sidecar when missing; or
(b) document that sidecar failures require `--overwrite` to remediate; or
(c) add a separate `--sidecar-only` mode for retry. Minimal patch:

```go
if !*overwriteFlag {
    csvExists, err := toast.SpacesKeyExists(ctx, client, bucket, csvKey)
    if err != nil { log.Fatalf("HeadObject %s: %v", csvKey, err) }
    metaExists, err := toast.SpacesKeyExists(ctx, client, bucket, toast.SpacesMetaKey(dateDir))
    if err != nil { log.Fatalf("HeadObject %s: %v", toast.SpacesMetaKey(dateDir), err) }
    if csvExists && metaExists {
        log.Printf("skip %s (CSV+sidecar already in Spaces)", dateDir)
        skipped++
        continue
    }
    if csvExists && !metaExists {
        log.Printf("repair %s (CSV present, sidecar missing — uploading sidecar only)", dateDir)
        // jump to sidecar upload block, skip CSV PutObject
    }
}
```

### WR-05: `dialWithRetry` always sleeps even on the final attempt — but skips final-attempt sleep correctly only because of the guard

**File:** `backend/internal/toast/sync.go:124-144`
**Issue:** Re-reading carefully, the loop is actually correct: `if i < len(backoffs)-1`
on line 138 prevents sleeping after the last failed attempt. So no behavioral
bug here. But there's a subtle dead variable: `wait` is bound from the range
over `backoffs` (line 127), but on iteration `i=0` we use `backoffs[0]=5s`
*after* attempt 1 fails, on `i=1` we use `backoffs[1]=15s` after attempt 2,
and on `i=2` we skip the sleep entirely. So the intended schedule is "5s
between attempts 1→2, 15s between 2→3, never 30s." The third value in the
slice is dead. The comment says "D-10 5s/15s/30s backoff schedule" but only
5s and 15s are ever actually slept.

This is a logic/documentation mismatch, not a bug — the worker still makes 3
attempts total. But operators reading the comment will expect a 30s pause that
never happens, and the slice element `30 * time.Second` is dead code.

**Fix:** Either rename the comment to "5s/15s schedule, 3 attempts" and drop
the 30s entry, OR restructure so the final attempt's failure path waits 30s
before returning (probably not what's wanted — that would just delay the
caller observing the failure). Cleanest:

```go
// Backoff schedule: 5s between attempts 1→2, 15s between 2→3. Three total attempts.
backoffs := []time.Duration{5 * time.Second, 15 * time.Second}
var lastErr error
for i := 0; i <= len(backoffs); i++ {
    client, err := New(SFTPConfig{...})
    if err == nil { return client, nil }
    lastErr = err
    if i < len(backoffs) {
        log.Printf("toast sync: SFTP dial attempt %d failed: %v — retrying in %s", i+1, err, backoffs[i])
        time.Sleep(backoffs[i])
    }
}
return nil, fmt.Errorf("sftp dial failed after %d attempts: %w", len(backoffs)+1, lastErr)
```

### IN-01: `dialWithRetry` does not honor `ctx` — `time.Sleep` can't be cancelled

**File:** `backend/internal/toast/sync.go:140`
**Issue:** `time.Sleep` is uncancellable. If the server is shutting down
during a 15s backoff, the worker's `ctx.Done()` won't be observed until the
sleep returns. Modest concern given 15s max in current schedule.

**Fix:** Plumb `ctx` through `SyncDate` → `dialWithRetry` and use
`select { case <-ctx.Done(): return ctx.Err(); case <-time.After(wait): }`.

### IN-02: `cmd/migrate-toast-archive` reads entire CSV into memory before upload

**File:** `backend/cmd/migrate-toast-archive/main.go:140-155`
**Issue:** `os.ReadFile(csvPath)` loads the whole file. Toast daily CSVs are
small (kilobytes to low-MB), so this is fine — but if it ever grows or someone
runs this on aggregated multi-year files, OOM is possible. Minor.

**Fix:** Stream with `os.Open` + pass the file directly as `s3.PutObjectInput.Body`:

```go
f, err := os.Open(csvPath)
if err != nil { ... }
defer f.Close()
st, _ := f.Stat()
client.PutObject(ctx, &s3.PutObjectInput{
    Bucket:        aws.String(bucket),
    Key:           aws.String(csvKey),
    Body:          f,
    ContentLength: aws.Int64(st.Size()),
    ContentType:   aws.String("text/csv"),
})
```

### IN-03: `migrate-toast-archive` exit code 1 contract is partially violated

**File:** `backend/cmd/migrate-toast-archive/main.go:25-29, 140-145`
**Issue:** The header doc says exit code 0 is "walk completed (per-date skips
are not errors)" and exit code 1 is "systemic Spaces failure." The "WARN: read
%s ... (skipping)" branch on a `os.ReadFile` failure (line 142-144) increments
`warned` and continues. A disk read failure on the source archive is arguably
systemic (not Spaces, but a precondition failure), and the operator might
expect non-zero exit on `warned > 0`. As written, the program returns 0 even
if every single date warns.

**Fix:** Either tighten the doc to reflect actual behavior ("non-zero exit
ONLY on Spaces failure") or count source-side warnings toward the exit code
threshold:

```go
if warned > 0 {
    log.Printf("done. uploaded=%d skipped=%d missing=%d warned=%d (non-zero exit due to warnings)",
        uploaded, skipped, missing, warned)
    os.Exit(2) // distinct from 1 (systemic) and 0 (clean)
}
```

### IN-04: `os.WriteFile(cachePath, csvBytes, 0o644)` is not atomic

**File:** `backend/internal/toast/sync.go:76`
**Issue:** The "atomic-ish file write" comment (line 71) is honest about this.
A SIGKILL between `os.WriteFile` and the subsequent `PutObject` leaves a
half-written cache file. The cache is documented as forensic-only (D-12), so
this is low-risk. For full atomicity, write to `cachePath + ".tmp"` then
`os.Rename` (POSIX-atomic on the same filesystem).

**Fix:**

```go
tmp := cachePath + ".tmp"
if err := os.WriteFile(tmp, csvBytes, 0o644); err != nil {
    return false, fmt.Errorf("toast sync: write tmp cache %s: %w", tmp, err)
}
if err := os.Rename(tmp, cachePath); err != nil {
    _ = os.Remove(tmp)
    return false, fmt.Errorf("toast sync: rename cache %s -> %s: %w", tmp, cachePath, err)
}
```

### IN-05: `runCycle` ignores `errors.Is(iErr, context.Canceled)` distinction

**File:** `backend/internal/toast/worker.go:133-140`
**Issue:** If the server shuts down mid-`RunIngest`, the cycle returns an error
that may be `context.Canceled`. `runCycle` will increment `consecSpacesFails`
and fire alerts on what is actually a clean shutdown. Low likelihood (ticks
are 12h apart, shutdowns are rare during the active ingest window) but
mis-attributes a noisy alert.

**Fix:**

```go
if iErr != nil {
    if errors.Is(iErr, context.Canceled) || errors.Is(iErr, context.DeadlineExceeded) {
        log.Printf("toast worker: ingest cycle cancelled: %v", iErr)
        return
    }
    log.Printf("toast worker: ingest cycle aborted: %v", iErr)
    syncSystemicErr = true
    lastSyncErr = iErr
}
```

The same applies to per-date errors in the sync loop.
