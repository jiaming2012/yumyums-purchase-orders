# Phase 22.1: HQ Toast ingest re-architecture — Spaces-first - Context

**Gathered:** 2026-06-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Move HQ's Toast ingest from direct SFTP → DO Spaces-backed pipeline. Sales-processor is fully decoupled; HQ owns both the SFTP→Spaces sync and the Spaces→DB ingest. A one-time migration CLI seeds the bucket from sales-processor's local Toast archive so the historical 90-day backfill window has data.

**Trigger:** Phase 22 verification revealed Toast's SFTP server purges files faster than the 90-day backfill assumes. Most dates returned "file does not exist" because they were already gone upstream. Toast SFTP is treated as ephemeral; DO Spaces is HQ's durable archive.

**This phase delivers:**
1. A combined worker (replaces Phase 22's `toast.StartWorker`): per 12h tick — sync SFTP→Spaces+cache for each date in window, then ingest Spaces→DB
2. A one-time migration CLI (`cmd/migrate-toast-archive`) that uploads sales-processor's historical archive to DO Spaces
3. A refactored ingest path (`toast.RunIngest`) that reads from DO Spaces only — no SFTP in the read path
4. A local filesystem cache at `backend/cache/toast/YYYYMMDD/` used for inspection/debugging only (no read fall-through)
5. Existing `cmd/sync-toast` CLI refactored to call the new combined sync+ingest path

**Explicitly NOT in this phase:**
- Schema changes (`menu_items`, `daily_menu_sales` unchanged from Phase 22)
- Menu tab UI changes (Phase 22-06 already complete; verification of live data is the only remaining Phase 22 task and closes when 22.1 ships)
- Phase 999.2 work (recipes, per-ingredient COGS attribution)
- DO Spaces lifecycle policies, multi-region replication, IAM scoping

**Carried forward from Phase 22 (locked, not re-decided):**
- Cold-start probe: `SELECT COUNT(*) FROM daily_menu_sales = 0` (Phase 22 D-02)
- Cold-start backfill window: last 90 days (Phase 22 D-01)
- Per-tick re-sync window: last 7 days for late corrections (Phase 22 D-04)
- Upsert idempotency: `ON CONFLICT (menu_item_id, business_date) DO UPDATE` (Phase 22 D-05)
- Voided lines excluded from `units_sold`/`gross_amount` (Phase 22 D-06)
- 3-level menu hierarchy preserved: `menu`/`menu_group`/`menu_subgroup` (Phase 22 D-07)
- `TOAST_SFTP_*` env vars + `TOAST_SYNC_INTERVAL` (Phase 22 — names unchanged)
- DO Spaces bucket = existing `hq.yumyums` (reuses `DO_SPACES_*` env vars from receipt pipeline)
- SFTP retry policy: 3x with 5s/15s/30s backoff (Phase 22 D-10)

<decisions>
## Implementation Decisions

### Spaces key layout & file naming

- **D-01:** **Bucket = existing `hq.yumyums`** (the same bucket photos and receipts use). Reuses `DO_SPACES_KEY`, `DO_SPACES_SECRET`, `DO_SPACES_BUCKET`, `DO_SPACES_REGION` env vars from `backend/.env`. No new env vars for storage.
- **D-02:** **Key prefix: `toast/YYYYMMDD/`** — flat partitioning by business date. Mirrors sales-processor's existing directory shape. Easy to list a date range with `Prefix=toast/2026`.
- **D-03:** **Canonical filename `ItemSelectionDetails.csv` + sidecar `ItemSelectionDetails.meta.json`.** The sync writer normalizes Toast's `113866_HQ_YYYYMMDD_ItemSelectionDetails.csv` to the canonical name on upload. The sidecar `.meta.json` captures `{original_filename, downloaded_at_iso, source}` where `source` is `"sftp"` (live sync) or `"migration"` (one-time CLI). Ingest reader uses the canonical name only; sidecar is operational metadata.

### Worker structure & cadence

- **D-04:** **Single combined worker** — `toast.StartWorker(ctx, cfg)`, fires every 12h (`TOAST_SYNC_INTERVAL` default). Each tick processes the rolling 7-day window (or 90-day window on cold start) in date order:
  1. **Sync phase** per date: if Spaces key exists, skip; else SFTP-fetch via existing `backend/internal/toast/sftp.go`; on success write to both Spaces AND local cache atomically (same bytes); on SFTP miss, graceful skip + INFO log.
  2. **Ingest phase** per date: read CSV bytes from Spaces (never from cache), parse via existing `toast.parseItemSelectionDetails`, upsert `menu_items` + `daily_menu_sales`.

  Refactors the existing Phase 22 worker (`backend/internal/toast/worker.go`) and `runCycle` into this combined flow.

- **D-05:** **SFTP miss is graceful skip + INFO log.** Log format: `toast sync: skip YYYYMMDD (not in SFTP)`. Expected behavior for dates past Toast's retention horizon (~14d typical). The migration CLI is what fills those gaps. Not an error, no alert.
- **D-06:** **DO Spaces unreachable → skip tick + Zoho Cliq alert after 3 consecutive failed ticks (~36h).** Server stays running. Worker logs ERROR each failed tick, increments an in-memory consecutive-failure counter, fires one Cliq message to the `purchaseandinventory` channel on the 3rd consecutive failure, and resets the counter on the next success.

  **This modifies Phase 22 D-12** (which made the worker fail-fast on missing SFTP key). Rationale: Spaces is now infrastructure broader than Toast ingest — the server has reasons to keep running even if Spaces is unreachable. The Cliq alert provides the same operator-visibility intent without coupling Toast availability to server availability.

  D-12's fail-fast on **`TOAST_SFTP_KEY_PATH` unset/unreadable** is preserved at boot (the sync path can't function without it; better to fail at startup than at first tick).

### Migration CLI (one-time historical seed)

- **D-07:** **New binary `cmd/migrate-toast-archive/main.go`**, separate from `cmd/sync-toast`. The two CLIs do different jobs: migrate uploads only (no DB writes), sync-toast runs the combined sync+ingest for a date range (mirrors what the worker does, but on demand).
- **D-08:** **Required `--source <path>` flag, no default.** Operator must explicitly pass the sales-processor archive root (`/Users/jamal/projects/yumyums/sales-processor/output/toast_reports`). No env var fallback, no relative-path default. This is intentional friction for a one-shot tool — keeps cross-repo paths out of HQ code.
- **D-09:** **Skip if Spaces key already exists (default); `--overwrite` flag to force re-upload.** Default behavior is safe re-run. `--overwrite` is for re-uploading after a bug fix or schema change. Idempotency check is a single `HeadObject` per date.
- **D-10:** **Upload only — no DB writes from the migration CLI.** Migration writes `ItemSelectionDetails.csv` + `ItemSelectionDetails.meta.json` (with `source: "migration"`) under `toast/YYYYMMDD/`. The next 12h worker tick parses + writes DB through the same ingest path used for live data. Single ingest code path, simpler to test.
- **D-11:** **Walk source dir, expect `<source>/YYYYMMDD/ItemSelectionDetails.csv` structure.** Matches sales-processor's archive layout exactly. Files not matching the pattern are skipped with a WARN log. Empty dates are skipped silently.

### Local cache policy

- **D-12:** **Cache path: `backend/cache/toast/YYYYMMDD/ItemSelectionDetails.csv`** + sidecar `.meta.json`. Gitignored (add to `backend/.gitignore` via this phase's plans).
- **D-13:** **Cache role is forensic/inspection only.** Ingest path always reads from DO Spaces — there is NO cache-first read. The cache exists so humans can `ls backend/cache/toast/` and inspect what was parsed on any given date without round-tripping to Spaces.
- **D-14:** **Sync path writes both Spaces AND cache atomically** (same bytes, same tick). On successful SFTP fetch: write cache file first, then upload to Spaces. If Spaces upload fails, the cache file is removed to keep cache and Spaces in lockstep (cache must never be more "current" than Spaces).
- **D-15:** **No cache eviction in v1.** A year of daily CSVs at YumYums volume is ~365 MB — trivial on the Windows-box disk. Revisit if cache exceeds 5 GB.

### Backfill / cold-start behavior

- **D-16:** **Cold-start uses the same 90-day window from Phase 22 D-01.** After the migration CLI runs, Spaces should already contain historical data; the cold-start worker tick will sync any recent dates SFTP still has, then ingest everything Spaces holds for the 90-day window.
- **D-17:** **Migration CLI does NOT bump cold-start state.** Cold start is detected by `SELECT COUNT(*) FROM daily_menu_sales = 0`. Migration only touches Spaces; DB stays empty until the worker's first tick. This is intentional — the worker is the single point of DB writes.

### Claude's Discretion

- **DO Spaces SDK approach:** Reuse the same `aws-sdk-go-v2/s3` client setup as `backend/internal/photos` (which receipt worker already uses). No separate config.
- **Cliq alert message format:** Brief — `"Toast sync degraded: 3 consecutive failed ticks talking to DO Spaces. Last error: <err>"`. No paging escalation, no retry-suppression beyond the failure counter.
- **Logging structure:** stdlib `log.Printf` with the existing `toast ingest:` / `toast sync:` prefixes (matches Phase 22 D-13). One INFO line per cycle summarizing dates processed.
- **HeadObject vs ListObjects for the migration idempotency check:** HeadObject per date is simpler; ListObjects with prefix is cheaper at scale. Either is fine — migration is a one-shot.
- **Where the combined worker lives:** Refactor in place — keep `backend/internal/toast/worker.go` and `runCycle`, replace the SFTP-direct logic with the sync+ingest combined flow. Don't rename for the sake of renaming.
- **Sync path SFTP retry policy:** Reuse Phase 22 D-10's 5s/15s/30s backoff inside the sync phase. After 3 retries on the same date in the same tick → graceful skip (same as a clean SFTP miss).

## Specific Ideas

- Migration CLI name: `cmd/migrate-toast-archive` (matches existing `cmd/sync-toast` naming style).
- Sidecar `.meta.json` shape:
  ```json
  {
    "original_filename": "113866_HQ_20260530_ItemSelectionDetails.csv",
    "downloaded_at_iso": "2026-06-03T07:59:33Z",
    "source": "sftp"
  }
  ```
- Cache atomicity rule: cache file written → Spaces upload attempted → on upload failure, cache file removed. This guarantees cache ⊆ Spaces.
- The user observed Phase 22's pipeline working end-to-end (worker boots, parses, writes DB) — just with most dates empty due to upstream purge. This phase is wiring + source-of-truth swap, not algorithm work.
