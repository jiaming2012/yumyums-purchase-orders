## The card

### E · `spike-e-reconnect-catchup` 🅢 — Activity 2, 5th spike (B-161)

**Question the exit status answers:** does a replicating RxDB client that was DISCONNECTED
while rows changed recover **everything** on reconnect via checkpoint pull — including a row
**UPDATED** without its `submitted_at` advancing (the `gte.<iso>` checkpoint's weak spot,
the same unreliable-watermark shape that disqualified `answered_at` for the polling relay)?

**Scope (2–4 lines):** Reuse spike C's harness end-to-end (scratch HQ Postgres on the real
schema, real `cmd/server`, real login, real `POST /api/v1/workflow/saveResponse`, the
spike relay projecting into the substrate) and spike D's substrate discipline. Subscribe an
RxDB client, confirm baseline replication, **sever its connection** (mechanism the card's own
call: kill the socket, block the port, or pause the replication — whichever severs most
attributably), write N rows through the real write path while dark — **at least one INSERT
and at least one UPDATE to a row the client already holds** — reconnect, and assert all N
changes arrive by pull within a bound. Exit status is the verdict.

- **Exit contract (sibling shape, the deliverable):** `0` = GREEN, full recovery observed;
  `1` = RED — ran, and catch-up demonstrably misses dark-window changes (**a successful
  spike**: it means the build cards need an explicit resync step); `2` = could not run (NOT
  a verdict); `3` = verdict reached but substrate could not be restored; `64` = usage.
  Collapsing 1 and 2 destroys the card.
- **Red-first (gate RF):** the natural red is **realtime-only recovery** — pull leg disabled
  on reconnect (`--no-pull` or equivalent). It MUST miss the dark-window rows or the green
  run's assertion set is vacuous (an ignored catch-up and a complete one look identical
  without it). Reproducible on demand via the flag, per C/D precedent.
- **Positive-arrival discipline (D's rule inherited):** the client must be OBSERVED
  replicating before the severing — a dead subscription and a recovered one must be
  distinguishable on both sides of the gap.
- **Teardown:** snapshot-before / assert-byte-identical-after on every shared substrate
  table it touches, exercised on the red path too (B-148's standard, both siblings meet it).
- **Isolation:** scratch Postgres on an ephemeral port, runtime-refused if it resolves to
  5432/5433/5434; substrate via the compose project only. C's harness already implements
  both — inherit, do not rewrite. Copy C's env-exec + occupied-port refusal (the `( … ) &`
  orphan-pid lesson, T-41).
- **Risk notes:** the UPDATE-case may honestly RED — that is the point; write the verdict
  either way. If severing cleanly proves hard, prefer the mechanism that keeps the
  *substrate* untouched (sever at the client) so A–D verdicts stay reproducible. The
  `submitted_at` semantics question (does HQ's write path advance it on every answer save?)
  is a FINDING to record, not a blocker — measure what the real write path does.
- **PARK note (narrow, operator-only):** park ONLY if the sole viable severing/recovery
  mechanism would require touching production or anything on :5433, adopting a paid/external
  service, or abandoning decision 126's read/write split (writes moving off
  `/saveResponse`/REST). A RED verdict is NOT a park. A gray area short of these routes
  through `night-crew decisions log` per CLAUDE.md §"Slate workflow" step 5.
