## The card

### Card 1 · `refusal-holds-before-sync` — the §8 refusal must hold BEFORE the campaigns replica has delivered

The B-432 unblocking card (roadmap Activity B; authored at morning triage 2026-09-05,
ledger T-54, decision 170), de-risked by three green spikes (goal ledger:
`spikes/activity-b-offline-first-replica/refusal-holds-before-sync.md` — **binding**,
including its six build-facts). The defect, demonstrated not asserted (spike 02 row 3):
with codes + offers in sync and the campaigns replica erroring, the shipped policy path
(`createCampaignPolicySource` Map empty → `null`; `submit-flow.js` `policyFor` null →
false) offers the offline override on a seeded `requires_online=true` $40 code to a
`canOverride` holder.

**Fix shape decided by the spike, with evidence (build-fact 3):** fail-closed at the
policy seam — for any **KNOWN code (`campaignId != null`) whose campaign is unresolved**,
answer `{requiresOnline: true}` regardless of replica readiness; a genuinely-unknown code
(`campaignId` null) keeps answering `null`, so **decision 166's ratified F2 affordance
survives by construction** (a known code always names a campaign, so "genuinely unknown"
never enters the fail-closed arm). This predicate subsumes readiness-gating (shape a) and
closes the "new campaign whose codes arrive first" window a bare readiness latch leaves
open. Spike 02 proved the shape refuses through the window (runs 1/4), stops over-refusing
the moment the replica is ready (run 5), preserves the unknown-code override + unverified
warning (run 2), and costs **zero new (state,event) pairs** on the strict machine.

**The owed items from the spike, binding:**
1. **The error latch (build-fact 1):** `error$` does NOT replay to late subscribers — the
   policy source subscribes before the replica starts and holds the last error itself.
   The emission carries the handler's HTTP status for free (spike 01), so replica-failure
   attribution needs no handler wrapping. The 150ms settle after
   `awaitInitialReplication()` is cheap insurance (the race did not bite on memory
   storage, but the browser runs Dexie — build-fact 2).
2. **The migration (build-fact 4):** `alter table public.scan_attempts add column
   policy_unresolved boolean not null default false` (name is the spike's candidate; the
   card may rename — the shape is what is proven) as a NEW numbered
   `supabase/migrations/` file, merged/applied **BEFORE** any client sends the field —
   pre-migration the extended landing body draws HTTP 400 `PGRST204`, the F-2 poison
   class (spike 03).
3. **Three named client edits (build-fact 5):** enqueue plumbing (`enqueueAttempt`'s
   destructure drops extra fields), `SCAN_ATTEMPTS_SCHEMA` version bump + device
   migration strategy (ajv rejects the field at v0), one landing-body whitelist line. The
   shipped push handler is otherwise forward-compatible (spike 03 drain leg green).
4. **The discriminator lands distinguishable:** replica-failure override
   `unverified_code=t, policy_unresolved=t` vs genuinely-unknown-code override
   `unverified_code=t, policy_unresolved=f`, both `status='accepted'` — **no new terminal
   status** (§9/§19 re-read held at spike time; a demand for one at build time is the
   PARK).
5. **The UI copy call (build-fact 6 — the card decides, against
   `docs/ui-design-rules.md`):** the `blockedOffline` branch copy "High-value offer:
   online verification is required" is misleading when the policy is *unresolved* rather
   than *known true*. Decide whether the unresolved case gets its own `data-branch` +
   copy ("can't verify this campaign yet — syncing"); the branch-3 e2e's expected
   `data-branch` value follows from this call. A blank or misleading render is a defect
   (UI-R class), not a nice-to-have.
6. **ONE validation run (the goal ledger's Comebacks, GAP-1):** re-execute spike 02 with
