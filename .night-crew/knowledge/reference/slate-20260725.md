## Cards

### 1. F1 · `workflow-submission-status-default` *(Go fix + red-first, S–M, ~45–90 m)*

`checklist_submissions.status` is `TEXT NOT NULL DEFAULT 'pending'` with
`CHECK (status IN ('pending','approved','rejected','completed'))`
(`backend/internal/db/migrations/0011_checklist_submissions.sql:9`). The insert in
`submitChecklist` (`backend/internal/workflow/repository.go:709`) never sets the column, and
nothing moves it for a `requires_approval:false` template — only `approveItem` (`:1141`) and
`rejectItem` (`:1187`) write it, and neither runs for a no-approval submission. Those rows read
`'pending'` server-side forever.

**The roadmap calls this "harmless today." Verify that claim first — it may be understated.**
`pendingApprovals` (`repository.go:995–1010`) filters on `s.status = 'pending'` and **does not
filter on `requires_approval` at all**. It is saved today only by its `ta.assignment_role =
'approver'` join: a no-approval template with no approver assignment produces no row. But nothing
in the schema or the create/update gate **forbids** an approver assignment on a
`requires_approval:false` template — `requires_approver_test.go:157–171` confirms the gate is
deliberately narrow (that combination "must still be accepted"). If such a template exists, its
submissions leak into a real user's approvals queue permanently.

(a) **Red-first, two tests, both failing before any fix:**
   (i) invariant — submit against a `requires_approval:false` template; assert the row's `status`
   is not left at `'pending'`;
   (ii) leak — seed a `requires_approval:false` template **with** an approver assignment, submit,
   assert the submission does **not** appear in that approver's pending queue. If (ii) does not go
   red, say so and record why — a red-first claim that never went red is not evidence.

(b) **Fix, decided — do not re-open these as forks:**
   - **Normalize at insert to `'completed'`.** That value is **already permitted by the existing
     CHECK constraint and is currently unused**, so this adds **no new lifecycle row and needs no
     migration**. `'approved'` is semantically wrong (nobody approved it) and would pollute the
     approvals audit trail.
   - **Gate `pendingApprovals` on the submission's own snapshot**, not the live template flag:
     prefer `(s.template_snapshot->>'requires_approval')::boolean IS NOT FALSE` over
     `t.requires_approval`. Reason: consistent with the repo's already-signed frozen-at-submit
     semantics (`.night-crew/knowledge/designs/editprop-frozen-at-submit.md`), and it does not make
     a genuinely-pending submission vanish from the queue when someone later flips the template's
     flag. **Verify the snapshot actually carries `requires_approval`** before relying on it —
     `TemplateInput` declares it (`model.go:142`) and the snapshot is `json.Marshal(tmpl)` at
     `repository.go:695`, but confirm against a real row; if it does not, fall back to
     `t.requires_approval` and **say in the merge-intent that you did and why**.
   - **No backfill of historical rows.** The `pendingApprovals` gate makes existing `'pending'`
     rows harmless immediately; a data migration over prod history is an attended act and not worth
     the deploy risk here. Record the residue in the HANDOFF as a known, bounded artifact.

(c) Footprint — Owns: `backend/internal/workflow/repository.go` (insert + `pendingApprovals`).
   Touches: `backend/internal/workflow/*_test.go`, and `tests/workflows.spec.js` /
   `tests/persistence.spec.js` if the leak is provable at the E2E layer. **All mapped seams →
   subset suite.**

**PARK triggers:** (i) the snapshot does **not** carry `requires_approval` *and* the live-flag
fallback changes behaviour for an existing pending submission → park with the evidence, do not
guess the semantics; (ii) an existing test or fixture depends on no-approval submissions reading
`'pending'` → that is a contract question, park it rather than editing the expectation.
→ Eng · QA KR2 (red-first evidence in the WO record).

### 3. W2 · `sync-spike-rxdb-replication` *(first-of-kind client spike, ~2 h 00 m – 4 h 15 m — droppable tail)*

**Operator ask, 2026-07-25: the spike must exercise RxDB itself, not just the stack beneath it.**
W1 proves Supabase accepts our token; W2 proves **RxDB actually replicates over it**. Runs only if
W1 landed with a GO and there is real time left (§"Tail discipline").

(a) **Isolated Node harness** at `.night-crew/qa/spike-supabase/rxdb/` with its **own**
`package.json` + lockfile — `rxdb` and `@supabase/supabase-js`. **The repo-root `package.json` is
HARD-untouched**; that is the Playwright environment for every card in the repo.

(b) **Define one RxDB collection** matching W1's verified self-hosted table contract (text PK,
`_deleted`, `_modified`), against a single throwaway table — **not** the real checklist domain
model. Modelling the real domain is `sync-rxdb-schema-and-replication`'s job; W2 answers "does the
mechanism work," not "what is our schema."

(c) **Prove replication in BOTH directions, separately and explicitly:**
   - **push** — write locally in RxDB, observe the row in Postgres via PostgREST;
   - **pull** — write directly in Postgres, observe RxDB converge without a client restart.
   A one-directional proof is the most common way this kind of spike fools itself. Show both, with
   the observed output.

(d) **Observe last-write-wins rather than assuming it.** The explore session chose LWW with no
custom conflict handler. Construct one concurrent-write case and **record what actually happens** —
including which clock decides and whether a write is silently lost. If the observed behaviour is
not the LWW the decision assumed, **that is a finding for the operator, not something to correct in
code.** Record it and let it route.

(e) **Answer the licensing and storage question — this is a go/no-go input, not trivia.** Determine
which RxDB storage the real PWA would use in a browser and **whether it is free or premium-licensed
under RxDB's current terms**. My reading is that the Dexie-based storage is the free browser path
and the IndexedDB storage is premium — **verify against RxDB's current license page rather than
trusting that**, and record the answer with its source. A premium dependency is a cost the operator
must know about *before* four cards are built on it. Also state plainly **what a Node-side proof
does and does not establish**: it proves the replication protocol, **not** browser storage
behaviour, not service-worker interaction, and not PWA offline semantics. Naming that limit is part
of the deliverable.

(f) **Also settle:** is RxDB's Supabase replication a **supported plugin** or a **documented example
built on `replicateRxCollection`** that we would maintain ourselves? The BACKLOG entry calls it a

## Dispatch mode

**SERIAL — F1 → W1 → W2.** The §5 criteria, applied:

- **Criterion 1 (prior clean orchestrator run): MET.** `overnight-20260724` completed cleanly under
  serial dispatch; `overnight-20260722` ran 2-track concurrent with 0 collisions.
- **Criterion 2 (bounded overlap): MET, trivially** — F1's and W1's footprints are fully disjoint,
  and W1→W2 share by design (W2 consumes W1's stack). On footprint alone, concurrency would be safe.
- **Criterion 3 (merge-intent "what must survive"): MET** — all three can state it.
- **What decides it is none of those: it is the suite.** All three run Playwright legs, and W1/W2
  pay the **full suite, which contains `sync.spec.js:1198`** — proven flaky at **~16 % overall and
  ~20 % under a concurrent Playwright suite** (`reference/1198-flake-reproduction-20260721.md`).
  Concurrent dispatch manufactures exactly the contention condition that flake needs. And because
  **night-crew's gate parses Go per-test but collapses Playwright to a single failure atom**, a red
  there cannot be attributed — the gate cannot distinguish "this card broke it" from "already red."
- **And the arithmetic is against it anyway.** W1→W2 are strictly serial by dependency, so
  concurrency could only overlap F1 — buying 45–90 m off a 6–12 h night, at ~2× burn, in exchange
  for an unattributable red at roughly 1-in-5. Serial is the cheap answer.
- **Burn rate is the operator's to weigh, not the planner's to assert** — the account's quota is
  invisible here (§15w). It was not the deciding factor either way.

**Order — F1 first, spikes after, and this is deliberate against the usual instinct:**
- F1 first guarantees the night produces **at least one merged card** even if W1 parks at 3 am on a
  dead registry. The reverse order risks a zero-merge night.
- F1's subset **excludes `sync.spec.js` entirely**, so it cannot be reddened by the known flake — a
  clean early signal before the box gets loaded by Supabase containers.
- W1 then gets the bulk of the night on a tree F1 has already proven green; W2 takes the tail, where
  its droppability costs nothing.
- §2's "riskiest last" is honoured: W2 is last, and W1 — the widest-variance card — sits where a
  long run cannot squeeze anything that matters.

A rate-limit stall has nothing to degrade to — the run is already serial.
