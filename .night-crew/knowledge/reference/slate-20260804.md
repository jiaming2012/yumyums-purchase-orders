### A1 · `e2e-gate-database-isolation` — 75–120m — **closes B-76**

> *As the owner, I want a failing test to mean the code is broken, so that I am not deciding
> whether to ship based on last week's leftover data.*

**Scope.** `night-crew.toml:33-34` runs `npx playwright test` directly for both `suite` and
`subset`. The only `DROP DATABASE IF EXISTS hq_test_e2e` / `CREATE DATABASE` lives in
`Taskfile.yml:53-59` under `task test`, and `playwright.config.js` has **no `globalSetup`**. So no
night-crew gate leg — full or subset — has ever reset the e2e database. Decision **131** already
reproduced the effect: the merged tree scored 777/6/1 on a fresh DB against the base's 758/6/4, and
the shared DB now reds three onboarding tests where it once red one.

**Fix:** put the reset where it cannot be bypassed — a `globalSetup` in `playwright.config.js`
guarded to **refuse any database whose name is not a test database** (a guard that fails loud beats
a default that eats a dev DB — B-16/B-35's lesson) — or point `[e2e] suite`/`subset` at a resetting
target. Either way it must fire on the **subset** path, which is the one that gets used most.

**Acceptance (this is Wave 0's gate):** a *subset* invocation demonstrably resets the database.
Red-first: show the current subset path leaving rows behind, then show it clean.

**Footprint:** `playwright.config.js`, `night-crew.toml`, `Taskfile.yml`, a new spec under `tests/`,
`BACKLOG.md`, `roadmap.md`.

🛑 **Do NOT touch `playwright.config.js:60`'s repo-wide `serviceWorkers: 'block'` (B-15).** Every
prior card has held that line.

### A6 · `app-version-badge` — 45–75m — 🅢 **STRETCH** — closes D-KR2b's evidence method

> *As the owner, I want the app to tell me which version it is running, so that I can confirm a
> deploy reached my phone without staging a photograph of it.*

**Scope.** A discreet version line (`index.html` footer). Ledger T-33 decision **133**.

🛑 **THE SOURCE IS THE DESIGN. Read the precached `version.json`. NEVER `/api/v1/health`.** The
server's `frontend_version` is always current — it was never wrong in T-21d — so an API-fed badge
would display the correct version on a phone frozen on the old bundle and **hide the defect it
exists to catch**. `version.json` is precached and served cache-first; it reports what *this
device's bundle* is, which is the only value capable of being stale.

**Recommended:** show the cached value beside the server's `frontend_version` so the app diagnoses
its own staleness. Most plumbing exists — `build-sw.js:291` writes the file and says why; no page
displays it.

**Footprint:** `index.html`, a test asserting the value is read from the precached file and not the
API, `sw.js` (regenerate after merge), `roadmap.md`.
