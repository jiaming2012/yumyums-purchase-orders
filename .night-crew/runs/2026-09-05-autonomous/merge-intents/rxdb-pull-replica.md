## Engineering calls (recorded for the merge record)

1. **Checkpoint shape — id tiebreak, not over-fetch:** checkpoint is
   `{updated_at, id}`; the pull predicate is the PostgREST keyset tree
   `or=(updated_at.gt."TS",and(updated_at.eq."TS",id.gt."ID"))` with
   `order=updated_at.asc,id.asc`. Chosen over the one-row over-fetch because a
   same-`updated_at` group LARGER than one batch defeats `gte`+client-skip entirely
   (the server returns the same first rows forever → zero new docs while rows remain
   — a livelock, not just a re-read). The keyset walks any tie group deterministically.
   Both spike build-facts honored: cursor components URL-encoded (`+00:00`), values
   double-quoted inside the logic tree.
2. **One table, two replicas:** the roadmap defers one-vs-two tables to "Activity A's
   schema call"; Activity A built ONE table (`public.codes` — no entitlements table in
   the committed migrations). So the offers replica is the SAME table pulled with the
   `expires_at > now()` bound, keyed locally on `token_hash` — which under §10's
   identity-code model IS the customer hash the device computes from the scanned QR.
   `resolveOffers(hash)` returns every live (unredeemed, unexpired) row for that hash:
   length 0..1 tonight, length N unchanged when the identity-code card lands. NO
   schema change was needed → the PARK note did not trigger.
3. **Redemption state is NOT server-filtered out of the offers pull** (no
   `redeemed_at=is.null` filter): a filtered-out redemption would never reach the
   replica and the offline offer list would stay stale-positive. Redeemed rows flow
   through the pull as updates; `resolveOffers` excludes them locally.
4. **Module layout — dependency injection, not bundle imports:**
   `marketing/sync/*.js` import nothing; the RxDB primitives, fetch, and the Realtime
   client arrive as parameters. The Node harness injects the QA rxdb
   (memory storage + dev-mode + ajv validation); the browser injects the vendored
   bundle (Dexie). Identical mechanism code runs in both — which is what makes the
   standalone harness a real gate on the shipped modules.
5. **Vendored-surface widening lives here** (rationale in Shared files above).
